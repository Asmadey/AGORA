## 0. Новые переменные в `.env.local`

Модель ролей изменилась, добавьте:

```
POSTGRES_USER=agora
POSTGRES_PASSWORD=...            # openssl rand -base64 24 — суперпользователь, только миграции
POSTGRES_DB=agora
AGORA_APP_PASSWORD=...           # openssl rand -base64 24 — рабочая роль приложения
AGORA_SHARE_PASSWORD=...         # openssl rand -base64 24 — публичные ссылки
MONGO_USER=agora
MONGO_PASSWORD=...
MONGO_DB=agora
```

**Почему отдельные роли.** RLS не действует на суперпользователя вообще: под
`postgres` кросс-арендаторной изоляции нет, сколько политик ни пиши. Поэтому:

| Роль | Назначение |
|------|-----------|
| `postgres` | суперпользователь, только миграции |
| `agora_login` | под ней подключаются web и worker; **прав не имеет**, NOINHERIT |
| `agora_app` | рабочая роль, NOSUPERUSER NOBYPASSRLS; включается через `SET LOCAL ROLE` |
| `agora_share` | публичная страница отчёта, только чтение по токену |

Соединение открывается безвластной ролью, права появляются внутри транзакции и
умирают вместе с ней. Забытый `SET LOCAL ROLE` даёт отказ в доступе, а не тихую
выдачу чужих данных — это и есть смысл `NOINHERIT`.

## 1. Пересоздать том Postgres

⚠️ Скрипты `docker-entrypoint-initdb.d` выполняются **только на пустом томе**.
Если Postgres уже поднимался в Pass 1, миграции не применятся.

```bash
docker compose -f infra/docker-compose.yml --env-file .env.local down -v
docker compose -f infra/docker-compose.yml --env-file .env.local up -d
docker compose -f infra/docker-compose.yml logs postgres --tail 30
```

В логах должно быть `AGORA: логин-роли agora_login и agora_share_login готовы`.
`down -v` сносит данные — на этом этапе терять нечего, но дальше так делать нельзя.

## 2. Поведенческая проверка изоляции

```bash
pip install "psycopg[binary]"

export DATABASE_URL="postgresql://agora_login:$AGORA_APP_PASSWORD@localhost:5432/agora"

python3 evals/tests/test_task02_db_rls.py     # CDD-тест задачи #2
python3 evals/check.py                         # метрика rls_tenant
```

Верификатор проверяет три вещи, а не одну:

1. из-под арендатора A строки B не видны ни в одной таблице;
2. **без** тенант-контекста выборка пуста — default deny, а не «вся таблица»;
3. записать строку чужому арендатору нельзя (`WITH CHECK`).

Третий пункт нужен потому, что `USING` без `WITH CHECK` защищает чтение, но
разрешает INSERT чужих строк — классическая половинчатая настройка RLS.

## Что появилось в Pass 2

**Postgres** — 16 таблиц с `FORCE ROW LEVEL SECURITY`:
идентичность (`users`, `teams`, `team_members`), настройки, проекты, персоны и наборы,
портреты, файлы контекста, промпты, анкеты, прогоны, отчёты, шеринг + аудит просмотров,
чат-треды и сообщения. Поля под будущие задачи заложены сразу: `prompts_snapshot`,
`replication_count`, `parent_task_id`, `carry_over_memory`.

**Три решения, которые стоит знать:**

*Промпты читаются иначе, чем правятся.* Резолв «активная версия арендатора → дефолт»
требует видеть чужие строки (`tenant_id IS NULL`). Поэтому SELECT разрешает свои +
дефолтные, а INSERT/UPDATE/DELETE — только свои. Иначе арендатор смог бы отредактировать
seed-промпт и сломать его всем остальным.

*Условия жизни публичной ссылки живут в политике, а не в коде.* `revoked_at IS NULL`
и `expires_at > now()` проверяет сама база. Код можно забыть обновить, политику обойти
нельзя. Токен хранится SHA-256 — дамп базы не даёт доступа по ссылкам.

*В MongoDB нет RLS.* Там изоляция — обязанность кода, поэтому `tenant_id` объявлен
`required` в каждой коллекции и стоит первым полем каждого индекса, а в слое доступа
есть `assert_tenant_filter()`, который роняет запрос без арендатора.

**Слой доступа** (`services/agent-core/agent_core/db.py`): единственный способ получить
курсор — `tenant_scope()`. Писать `WHERE tenant_id = ...` не нужно и не следует —
фильтрует RLS. 26 тестов, включая отказ на не-UUID и на инъекцию в имя роли.
