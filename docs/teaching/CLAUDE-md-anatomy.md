# Из чего состоит хороший `CLAUDE.md`

`CLAUDE.md` — файл, который агент читает первым в каждой сессии. Он же
единственное, что переживает конец контекста.

Отсюда критерий качества, отличный от «полноты»: **не «всё ли описано», а
«достаточно ли этого, чтобы не повторить вчерашнюю ошибку»**. Полный документ,
который не читают, хуже короткого, который читают.

---

## Три правила, определяющие всё остальное

### 1. Правило без цены не соблюдается

Сравните:

> ❌ Пишите качественный код и следуйте лучшим практикам.

> ✅ **Нативные npm-модули в `apps/web` запрещены.** `node_modules` общий для
> всех, кто открывает папку, а нативные пакеты собираются под конкретную
> платформу: установленный из Linux пакет ломает запуск на macOS. Это уже
> стоило нам одного прохода. Нужен argon2 — берите `hash-wasm` (WebAssembly).

Второе читают до конца, потому что там есть история. Первое пролистывают.

Формула: **что нельзя → почему → что вместо → чем это обошлось**.

### 2. Запрет без замены будет обойдён

Агенту нужно выполнить задачу. Если единственный известный ему путь закрыт, он
найдёт обходной — и это будет путь, о котором вы не подумали. Всегда указывайте
разрешённую альтернативу.

### 3. Исключение оформляется падающей проверкой, а не комментарием

Из `CLAUDE.md` AGORA, §5:

> Если отступление от правила неизбежно, к нему пишется тест, который красный,
> пока отступление в силе. Комментарий в миграции ничего не удерживает:
> временное решение живёт вечно ровно потому, что никто не знает, что оно ещё
> в силе.

## Структура: восемь разделов

Порядок не случаен — он идёт по времени жизни сессии агента.

### §1. Перед началом работы

Команды, отвечающие на вопрос «что здесь произошло без меня». Буквально
командами, а не описанием.

```bash
git fetch --all --prune
git log --oneline -15
gh pr list --state open
git worktree list
```

Плюс — какие файлы состояния прочитать и что в них искать.

### §2. Где работать: каталог и ветка

Как называется ветка, как не столкнуться с другим агентом, что запрещено (прямой
push в `main`).

Для многоагентной работы — обязательно про отдельный worktree. Общий
`node_modules` при параллельной работе ломается молча.

### §3. Порядок работы над задачей

Пронумерованный, с явной пометкой, что порядок не декоративный. В AGORA это CDD:

1. Красный тест по полю `cdd` — он **обязан** упасть и перечислить невыполненные
   условия.
2. Реализация до зелёного.
3. Проверки: типы, сборка, тесты, линт — конкретными командами.
4. PR по шаблону.

### §4. Кто выносит вердикт

Отдельный короткий раздел о том, что автор не закрывает свою задачу сам.
В AGORA: статус в графе ставит прогон в среде пользователя, а в PR пишется, что
подтверждено, а что осталось неподтверждённым.

Это единственная защита от «работает на моей машине», которая масштабируется.

### §5. Опасная подсистема

У каждого проекта есть одна, где ошибка не видна сразу. В AGORA это база: RLS,
миграции, роли. Раздел большой и подробный — по делу, потому что цена там выше.

Определите свою: платежи, права доступа, миграции данных, интеграция с внешним
API. И опишите её так же подробно.

### §6. Ограничения, которые уже стоили проходов

**Самый ценный раздел файла.** Список конкретных граблей, каждая с симптомом и
причиной. Пример:

> **`SET LOCAL app.tenant_id = $1` не работает.** Команда `SET` не принимает
> параметры запроса. Только `set_config('app.tenant_id', $1, true)`.

> **`pg` игнорирует поле `ssl`, если задан `connectionString`.** Разобранная
> строка перезаписывает явно переданные поля вместе с корневым сертификатом.
> Путь к сертификату передавайте параметром `sslrootcert` внутри самой строки.

Раздел растёт по ходу проекта. Пустой в первый день — это нормально; пустой на
третьей неделе означает, что уроки никто не записывает.

### §7. Секреты

Что не попадает в git, что считается скомпрометированным, что делать при утечке.
Прямо и без смягчений.

### §8. Как записать проход

Куда агент пишет результат работы, чтобы следующий его увидел. В AGORA это
`loop-state.json` с полями `did`, `verdict`, `findings`, `failed_hypotheses`,
`next`.

Поле **`failed_hypotheses`** важнее остальных: отрицательный результат экономит
чужой проход, а «всё получилось» не сообщает ничего.

## Шаблон для нового проекта

Скопируйте и заполните. Пустые разделы лучше удалить, чем оставить заглушками:
раздел-заглушка учит читателя пропускать разделы.

````markdown
# Правила работы над <ПРОЕКТ>

Над репозиторием работают несколько ИИ-агентов и человек. Агенты друг друга не
видят: у каждого своя сессия. Всё, что не записано в репозиторий, для остальных
не существует. Прочитайте этот файл целиком до первого изменения файлов.

## 1. Перед началом работы

```bash
git fetch --all --prune
git log --oneline -15
gh pr list --state open
```

Затем прочитайте: <файл состояния> — что сделано и что не сработало.

## 2. Каталог и ветка

Отдельный worktree на задачу: `git worktree add ../<проект>-<задача> -b task/NN`.
Прямой push в `main` запрещён.

## 3. Порядок работы над задачей

1. Тест по критерию приёмки — запустите, он обязан упасть.
2. Реализация до зелёного.
3. Проверки: `<команда сборки>`, `<команда линта>`, `<команда тестов>`.
4. PR по шаблону.

## 4. Задачу закрывает не автор

Статус ставит проверяющий по прогону в реальной среде. В PR пишите, что
подтверждено, а что осталось неподтверждённым.

## 5. <Опасная подсистема проекта>

<Правила. Каждое — с причиной и с тем, как выглядит нарушение.>

## 6. Ограничения, которые уже стоили времени

<Пополняется по ходу. Формат: что не работает → почему → что вместо.>

## 7. Секреты

`.env.local` в репозиторий не попадает. Ключи не вставляются в PR, комментарии и
переписку. Утёкший ключ перевыпускается — удаление файла ничего не отменяет.

## 8. Запись результата

После задачи допишите в <файл состояния>: что сделал, что проверено, **какие
гипотезы не подтвердились**, что делать дальше.
````

## Чего в `CLAUDE.md` быть не должно

| Не пишите | Почему | Куда вместо |
|---|---|---|
| Описание структуры каталогов | устаревает первым, агент видит её сам | `ARCHITECTURE.md` |
| Список сделанных задач | устаревает каждый день | файл состояния / трекер |
| Инструкции по запуску | это для человека | `README.md` |
| Пересказ документации фреймворка | агент знает её лучше | MCP context7 |
| «Будь внимателен», «пиши качественно» | не проверяемо, значит не действует | проверка в CI |

Общее правило: **в `CLAUDE.md` попадает то, чего агент не может узнать сам.**
Всё остальное — шум, который вытесняет важное из внимания.

## Как понять, что файл получился

Проверка на одном вопросе: **новый агент в чистой сессии, прочитав только этот
файл, сделает задачу без уточняющих вопросов?**

Если приходится объяснять что-то в чате повторно — это не недостаток агента.
Это отсутствующий абзац в `CLAUDE.md`, и написать его нужно сразу же, пока
понятно, какой именно.
