# Промпты по шагам — готовые формулировки

Промпты для демонстрации. Копируются как есть, `<в угловых скобках>` —
подставить своё.

**Общий принцип, который стоит проговорить один раз и потом только напоминать:**

> В каждом промпте должны быть четыре вещи: **что** сделать, **где** (файлы и
> папки), **чем** (версии и библиотеки) и **как проверить**, что получилось.
> Промпт без четвёртого пункта не имеет окончания — агент остановится там, где
> сочтёт нужным, а не там, где задача решена.

---

## 1. Инициализация проекта

### 1.1 Скелет

Не просите агента писать `package.json` с нуля — официальный стартер даёт
согласованный набор версий, а агент от себя соберёт то, что помнит с прошлого
года.

```bash
pnpm create next-app@latest web --typescript --tailwind --app --eslint --src-dir
```

Дальше — агенту:

```
Приведи свежесозданный проект в рабочее состояние.

Структура:
- src/app — роутинг. В каждом сегменте с загрузкой данных обязательны
  layout.tsx, loading.tsx, error.tsx; в корне ещё not-found.tsx
- src/components/ui — примитивы shadcn, вручную не редактируются
- src/components/<продукт> — компоненты продукта
- src/lib/server — всё серверное: база, аутентификация, внешние API.
  Подключи пакет server-only, чтобы импорт с клиента падал при сборке
- src/lib/env.ts — валидация переменных окружения через zod, вызывается при старте

Настрой:
- tsconfig: strict: true, пути @/ → src/
- .env.example со всеми переменными и комментарием к каждой
- .gitignore: .env.local

Проверка: pnpm build && pnpm lint && npx tsc --noEmit — чисто.
Покажи дерево файлов и объясни, что где лежит.
```

### 1.2 `CLAUDE.md` под проект

```
Составь CLAUDE.md для этого проекта — инструкцию для ИИ-агентов, которые будут
над ним работать в отдельных сессиях и не видят друг друга.

Разделы:
1. Что проверить перед началом работы (командами)
2. Ветки и порядок работы
3. Порядок выполнения задачи: тест → реализация → проверки → PR
4. Кто закрывает задачу (не автор)
5. Опасная подсистема проекта: <назови свою> — правила с причинами
6. Ограничения, которые уже стоили времени (пока пусто, будет пополняться)
7. Секреты
8. Куда записывать результат прохода

Требования к формулировкам:
- каждое правило: что нельзя → почему → что делать вместо
- не описывай структуру каталогов и не пересказывай документацию фреймворка:
  агент видит первое сам, а второе знает
- никаких «пиши качественно»: только проверяемое
```

## 2. Из ТЗ в архитектуру

Ключ — **запретить писать код на этом шаге**. Иначе агент начнёт с файлов и
подгонит решения под уже написанное.

```
Прочитай <путь к ТЗ>. Кода пока не пиши.

Верни:

1. Таблицу технологических решений: слой | выбор | альтернатива | почему выбрано
   именно это | чем платим. Слои: фреймворк, стейт, стили, база, аутентификация,
   фоновые задачи, файловое хранилище, развёртывание.

2. Файловую структуру до второго уровня с назначением каждой папки.

3. Схему данных: сущности и связи. Для каждого хранилища — одна строка, почему
   именно оно, а не то, что уже есть в проекте.

4. Три места, где эта архитектура сломается при росте, и признак, по которому
   это станет заметно.

Пункт 4 обязателен. Если нечего написать — значит архитектура не продумана,
а не идеальна.
```

### 2.1 Граф задач

```
На основе архитектуры составь граф задач в tasks.json.

Поля каждой задачи:
- id, subject, status
- blockedBy: [id, …] — задачи, без которых эта не начинается
- cdd: условие красного теста. Проверяемое утверждение с числом или точным
  фактом, а не описание задачи
- acceptance: что считать сделанным

Требования:
- задача — от половины дня до двух дней работы
- ни одной задачи без blockedBy, кроме первых
- cdd формулируется до кода: тест, написанный после реализации, проверяет то,
  что сделали, а не то, что требовалось

В конце покажи критический путь и назови задачи, которые можно делать параллельно.
```

## 3. Библиотеки и UI-киты

### 3.1 Подключение MCP

```bash
# Актуальная документация библиотек — против устаревших знаний модели
claude mcp add context7 -- npx -y @upstash/context7-mcp

# Забор страниц по ссылке — для работы по референсу
claude mcp add firecrawl -- npx -y firecrawl-mcp
```

Проверка, что context7 действительно работает, а не просто подключился:

```
Через context7 покажи актуальный способ настройки темы в Tailwind v4.
Скажи явно, что изменилось по сравнению с v3 и почему tailwind.config.js
больше не основной способ.
```

Если агент отвечает про `tailwind.config.js` как про основной путь — MCP не
подключился либо не используется.

### 3.2 UI-кит

```
Подключи shadcn/ui поверх Tailwind v4.

- npx shadcn@latest init, стиль new-york, базовый цвет neutral
- добавь: button, card, dialog, select, tabs, skeleton, sonner, form
- примитивы кладутся в src/components/ui и вручную не редактируются;
  всё своё — в src/components/<продукт>
- тёмная тема по умолчанию, палитра через @theme в globals.css
- через context7 сверься с актуальной документацией shadcn: CLI менялся

Проверка: pnpm build чисто, страница с кнопкой и диалогом рендерится
без предупреждений в консоли.
```

## 4. UI-каркас

### 4.1 Экран с нуля

Описываются **состояния**, а не внешний вид.

```
Свёрстай экран <название>.

Данные: <что показываем>
Действия: <что можно сделать>

Состояния — все четыре обязательны:
- загрузка: skeleton по форме будущего контента, не спиннер
- пусто: что это значит и что сделать дальше — с кнопкой действия
- ошибка: что произошло и что попробовать, плюс кнопка повтора
- данные: основной вид

Требования:
- Server Component по умолчанию; 'use client' только там, где есть интерактив,
  и в комментарии — почему
- адаптив от 360px
- фокус видим с клавиатуры, у интерактивных элементов есть доступные имена

Проверка: pnpm build чисто; покажи все четыре состояния скриншотами
или отдельным маршрутом /<экран>/preview.
```

### 4.2 Экран данных

```
Свёрстай таблицу <сущность> с сортировкой, фильтром и пагинацией.

- пагинация серверная, состояние в URL (?page=&sort=&q=) — ссылку можно переслать
- пустой результат фильтра и пустая таблица — разные экраны с разным текстом
- на мобильном таблица превращается в карточки, а не в горизонтальную прокрутку
- длинные значения обрезаются с подсказкой, строка не расползается

Проверка: перезагрузка страницы сохраняет фильтр и сортировку.
```

## 5. Вёрстка по референсу через Firecrawl

Три шага. Второй пропускать нельзя — именно он отличает работу по образцу от
копирования.

### Шаг 1. Забрать

```
Через firecrawl забери <URL>. Сохрани разметку и стили в scratch/reference/.
Ничего пока не верстай.
```

### Шаг 2. Разобрать в описание системы, а не в копию

```
На основе забранной страницы составь описание её дизайн-системы.
Разметку страницы не воспроизводи — нужно описание.

1. Сетка: контейнер, колонки, брейкпоинты
2. Ритм отступов: какая шкала используется (4/8pt?), назови значения
3. Типографика: размеры, интерлиньяж, насыщенности — сведи в шкалу
4. Палитра: роли цветов (фон, поверхность, текст, акцент, опасность),
   в токенах, а не «синий #1E6FFF»
5. Компоненты: перечисли встречающиеся типы блоков и их назначение
6. Что здесь работает хорошо и что бы ты сделал иначе

Результат — таблицы токенов, готовые перенести в @theme.
```

### Шаг 3. Собрать своё

```
По описанию из шага 2 собери <наш экран> на нашем стеке
(Next 15 + Tailwind v4 + shadcn).

- перенеси токены в @theme, названия наши: --color-surface, --space-4 и т.п.
- компоненты собери из наших примитивов в components/ui
- содержание, тексты, изображения и логотипы — наши. С референса берём
  структуру и ритм, не контент и не фирменный стиль

Проверка: pnpm build чисто, экран адаптивен от 360px,
контраст текста не ниже 4.5:1.
```

**Сказать студентам вслух:** структура и ритм — общее ремесло, их изучают по
чужим работам совершенно законно. Тексты, фотографии, логотипы и узнаваемый
фирменный стиль — чужая собственность. Граница проходит здесь, и она не
техническая.

## 6. Конфиги и зависимости

### 6.1 Добавление зависимости

```
Нужно <задача: например, хешировать пароли>.

Предложи два варианта библиотеки с ответом на вопросы:
- нативные модули есть? (важно: собираем в Docker на Linux, разрабатываем на macOS)
- размер и что тянет за собой
- когда последний релиз, кто поддерживает
- сколько кода нужно нам самим

Выбери один, обоснуй, поставь. Зависимость добавляй ровно одну.
```

Показательный ответ на этом примере: `@node-rs/argon2` быстрее, но нативный —
собранный на Linux пакет ломает запуск на macOS у соседа по репозиторию.
`hash-wasm` на WebAssembly работает везде.

### 6.2 Проверка, что зависимости объявлены

```
Напиши тест, который разбирает исходники через AST, собирает все внешние
импорты — включая объявленные внутри функций — и проверяет, что каждое имя
разрешается в текущем окружении.

Почему именно так: тяжёлые импорты часто прячут внутрь функций, чтобы не платить
за них при старте. Побочный эффект — модуль импортируется без ошибки, образ
собирается, сервис поднимается healthy, а ModuleNotFoundError ждёт первого
обращения к нужной ветке кода.

Сверять со списком в package.json/pyproject не нужно: часть пакетов приходит
транзитивно и по делу, такой тест краснел бы на правильном коде.
```

### 6.3 Валидация окружения

```
Сделай src/lib/env.ts: схема zod для всех переменных окружения, разбор при
импорте модуля, экспорт типизированного объекта.

- серверные и клиентские переменные разделены; клиентские только NEXT_PUBLIC_*
- при отсутствии обязательной переменной — падение при старте с перечислением
  всех недостающих сразу, а не первой попавшейся
- обнови .env.example

Причина: переменная, забытая в проде, иначе обнаружится на первом запросе
пользователя, а не при выкладке.
```

## 7. Промпты, которые стоит показать как «так не надо»

| Плохо | Что не так | Как надо |
|---|---|---|
| «Сделай красиво» | нет критерия — агент выберет свой | описать состояния и ограничения |
| «Исправь ошибку» | без текста ошибки агент угадывает | вставить вывод целиком |
| «Добавь тесты» | получите тесты на геттеры | назвать сценарий отказа |
| «Отрефактори проект» | огромный диффф, который не отревьюить | одна цель, один каталог |
| «Используй лучшие практики» | у модели они на дату обучения | назвать версию, дать context7 |

## 8. Слэш-команда: одноразовое указание → процедура

Финальный аккорд лекции. Всё, что вы объясняете агенту чаще одного раза, должно
стать файлом.

`.claude/commands/new-screen.md`:

```markdown
---
description: Новый экран со всеми четырьмя состояниями
---

Создай экран $ARGUMENTS.

Обязательно все четыре состояния: загрузка (skeleton по форме контента),
пусто (с действием), ошибка (с повтором), данные.

Server Component по умолчанию; 'use client' — только для интерактива,
с комментарием почему.

Проверка: pnpm build чисто, покажи все четыре состояния.
```

Дальше в чате достаточно `/new-screen список проектов`.

Мысль, которой стоит закончить: разница между «пользуюсь ИИ» и «работаю с ИИ» —
в том, накапливается ли что-нибудь между сессиями. Промпт, сказанный в чате,
исчезает. Промпт, записанный в файл, становится частью проекта.
