# Инициализация проекта с ИИ-агентами — план лекции

Материал рассчитан на 90 минут с живой демонстрацией. AGORA используется как
рабочий пример: показывать состоявшийся проект честнее, чем свежесозданный
скелет, — в нём видно, во что превращаются решения через три недели.

**Файлы к лекции:**

| Файл | Зачем |
|---|---|
| `docs/teaching/LECTURE.md` | этот план |
| `docs/teaching/CLAUDE-md-anatomy.md` | из чего состоит хороший CLAUDE.md |
| `docs/teaching/prompts-cookbook.md` | готовые промпты по каждому шагу |
| `docs/ARCHITECTURE.md` | пример документа архитектуры |
| `docs/AGORA_HANDOFF.md` | пример контекстного документа |
| `docs/TEST_case.md` | пример приёмки |
| `CLAUDE.md` | боевой протокол, выстраданный |

---

## Главная мысль лекции

Скажите её в первые три минуты и возвращайтесь к ней на каждом шаге:

> Агент не помнит вчерашний день. Всё, что не записано в репозиторий, для
> следующей сессии не существует.

Отсюда следует всё остальное. Папка `.claude/`, `CLAUDE.md`, документы в `docs/`
— это не бюрократия и не «оформление». Это **единственная память проекта**.
Студент, который это понял, дальше сам догадается, что писать; студент, который
не понял, будет каждый раз объяснять агенту проект заново и считать, что модель
слабая.

Второй тезис, менее очевидный:

> Правило без цены не соблюдается.

В `CLAUDE.md` AGORA почти каждый абзац заканчивается фразой вида «это уже стоило
нам одного прохода». Правило с историей отказа читают. Правило «пишите хороший
код» пролистывают.

## Шаг 1 (20 мин) — структура проекта и `CLAUDE.md`

### Что показать вживую

```bash
git clone <репозиторий> && cd AGORA
ls -a
```

Разберите дерево по слоям, называя **назначение**, а не содержимое:

```
CLAUDE.md          протокол работы — читается агентом первым
AGENTS.md          то же для агентов других вендоров
README.md          как запустить — для человека
.claude/           настройки инструмента: агенты, команды, хуки
docs/              контекст: PRD, архитектура, приёмка, передача
apps/ services/    код
packages/shared/   контракты между частями
evals/             как проверяется, что сделано
prompts/           промпты моделей как исходники
```

### Что говорить про `.claude/`

```bash
ls .claude/
# agents  commands  hooks  settings.local.json  skills
```

- `agents/` — специализированные подагенты (планировщик, ревьюер, отладчик).
  Каждый со своим набором инструментов и своей моделью.
- `commands/` — слэш-команды: повторяемая процедура, записанная один раз.
- `hooks/` — перехват действий; например, запретить коммит с непройденным линтом.
- `settings.local.json` — локальные разрешения, **не** в git.

Ключевая мысль: `.claude/` — это то, что превращает разовые указания в
процедуру. «Проверь линт перед коммитом» сказанное в чате — работает один раз.
Записанное в хук — работает всегда.

### Что говорить про `docs/`

Покажите разделение по адресату — оно неочевидно и именно на нём чаще всего
разваливается документация:

| Документ | Кому | Отвечает на вопрос |
|---|---|---|
| `AGORA_PRD_FINAL.md` | заказчику | что за продукт и зачем |
| `ARCHITECTURE.md` | разработчику | где что лежит и почему |
| `AGORA_HANDOFF.md` | следующему агенту | в каком состоянии проект прямо сейчас |
| `TEST_case.md` | проверяющему | что увидеть глазами, чтобы поверить |
| `PROGRESS_REPORT.md` | заказчику | что готово, что нет, чем заблокировано |

Один файл «документация» на все пять ролей не читает никто, потому что каждому
читателю в нём 80% лишнего.

### `CLAUDE.md` — 10 минут, самое важное в шаге

Откройте `CLAUDE.md` AGORA и покажите **§6 «Ограничения, которые уже стоили
проходов»**. Прочитайте вслух один пункт целиком:

> **Нативные npm-модули в `apps/web` запрещены.** `node_modules` — общий для
> всех, кто открывает папку, а нативные пакеты собираются под конкретную
> платформу: установленный из Linux пакет ломает запуск на macOS. Нужен argon2 —
> берите `hash-wasm` (WebAssembly), а не `@node-rs/argon2`.

Три части: **что нельзя**, **почему**, **что вместо**. Все три обязательны.
Запрет без замены агент обойдёт — ему надо выполнить задачу.

Дальше — `docs/teaching/CLAUDE-md-anatomy.md`, там разбор по разделам и шаблон.

## Шаг 2 (20 мин) — из ТЗ в архитектуру

### Что показать

Порядок, в котором это делается, важнее содержания:

```
ТЗ (PRD) → выбор технологий → граф задач → файловая структура → код
```

Пропуск любого шага стоит переделки. Чаще всего пропускают **граф задач** — и
получают проект, где всё начато и ничего не закончено.

### Живая демонстрация: PRD → архитектура

Промпт целиком — в `prompts-cookbook.md`, раздел 2. Суть: агент читает PRD и
возвращает **не код**, а таблицу решений с альтернативами.

Покажите результат на AGORA — `docs/ARCHITECTURE.md`, раздел 5 «Данные»: четыре
хранилища, у каждого одна строка «почему именно оно». Спросите аудиторию: можно
ли было обойтись одним Postgres? Ответ — да, и это правильный вопрос; в
документе видно, чем платим за четыре.

### Граф задач вместо списка задач

Покажите `evals/state/tasks.json`:

```json
{
  "id": 5,
  "subject": "Persona Generator",
  "status": "done",
  "blockedBy": [4, 26],
  "verifies": ["persona_grounding", "subjective_persona_realism"],
  "cdd": "на эталонном конфиге распределения по age_group/geo/gender отклоняются от корпуса не более чем на 0.10; повторный прогон на том же seed → diff == 0",
  "acceptance": "Генерация по методологии PRD §10 …"
}
```

Обратите внимание студентов на четыре поля:

- **`blockedBy`** — граф, а не список. Агент берёт только задачу с закрытыми
  зависимостями. Без этого поля два агента начнут одно и то же с разных концов.
- **`cdd`** — условие красного теста, **написанное до реализации**. Это не
  описание задачи, а проверяемое утверждение с числом.
- **`acceptance`** — что считать сделанным.
- **`verifies`** — какую метрику проекта задача закрывает. Задача, которая не
  закрывает ни одной, — кандидат на вылет.

### Одна фраза, которую стоит записать студентам

> `cdd` формулируется до кода. Тест, написанный после реализации, проверяет то,
> что вы сделали, а не то, что требовалось.

## Шаг 3 (15 мин) — библиотеки и UI-киты через команды агенту

### MCP Context7 — зачем

Модель знает библиотеки на момент обучения. Tailwind v4 переехал с
`tailwind.config.js` на `@theme` в CSS; React Router v7 сменил API; shadcn
переехал на новый CLI. Агент без доступа к актуальной документации уверенно
напишет прошлогодний код — и это худший вид ошибки, потому что он выглядит
правильным.

Context7 отдаёт агенту документацию нужной версии по запросу.

```bash
claude mcp add context7 -- npx -y @upstash/context7-mcp
```

Проверка, что подключилось: попросите агента «покажи актуальный синтаксис
конфигурации Tailwind v4 через context7» и сверьте с сайтом.

### shadcn/ui — правильный способ

```bash
npx shadcn@latest init
npx shadcn@latest add button card dialog select tabs
```

Что объяснить: shadcn — **не библиотека компонентов**, а генератор. Он кладёт
исходники в `components/ui/`, и дальше это ваш код. Отсюда правило AGORA:

> `components/ui/` — сгенерированное, руками не правим.
> `components/agora/` — компоненты продукта.

Смешение этих двух папок означает, что обновить примитив станет нельзя: ваши
правки затрутся при `add` или вы побоитесь его запускать.

### Формулировка команды агенту

Плохо: «подключи UI-кит».
Хорошо: **что, какой версии, куда, и как проверить**:

> Подключи shadcn/ui поверх Tailwind v4. Примитивы — в `components/ui/`,
> не редактируй их вручную. Добавь button, card, dialog, select, tabs, skeleton.
> Тему возьми тёмную, цвета в `app/globals.css` через `@theme`.
> Проверка: `pnpm build && tsc --noEmit` — чисто, и `/` рендерится без ошибок в консоли.

Последняя строка — самая важная. **Задача без критерия проверки не имеет
окончания.**

## Шаг 4 (20 мин) — UI-каркас по промптам и по референсу

### Вариант А: с нуля, по описанию

Промпты — в `prompts-cookbook.md`, раздел 4. Принцип: описывать **состояния**, а
не внешний вид.

У любого асинхронного экрана их четыре, и три из них забывают:

```
загрузка → пусто → ошибка → данные
```

Экран, нарисованный только для «данных», в продакшене выглядит сломанным ровно
в тот момент, когда пользователю тяжелее всего — когда что-то пошло не так.

### Вариант Б: по референсу через Firecrawl

Задача: взять чужой сайт как образец структуры и сверстать свой по его подобию.

```bash
claude mcp add firecrawl -- npx -y firecrawl-mcp
# нужен FIRECRAWL_API_KEY
```

Порядок, который работает:

1. **Забрать** страницу — Firecrawl отдаёт разметку и стили.
2. **Разобрать в структуру, а не в копию.** Просите агента выдать *описание*:
   сетка, ритм отступов, шкала типографики, палитра, набор компонентов.
   Это шаг, который студенты пропускают — и получают чужой сайт с подменёнными
   надписями.
3. **Собрать своё** на своём стеке по этому описанию.

Формулировка для шага 2 есть в `prompts-cookbook.md`, раздел 5.

**Скажите про право явно.** Верстать по образцу структуры — нормально;
копировать текст, изображения, логотипы и фирменный стиль — нет. Студенты об
этом не думают, а стоит это дороже, чем неудачный лейаут.

## Шаг 5 (15 мин) — конфиги и зависимости

### Не просите «сгенерируй package.json»

Попросите **задачу**, а зависимости пусть появятся как следствие. Иначе получите
список пакетов, часть из которых не нужна, а часть несовместима.

Правильная последовательность:

```bash
pnpm create next-app@latest web --typescript --tailwind --app --eslint
cd web && npx shadcn@latest init
```

То есть: официальный стартер даёт согласованный набор версий, а агент дальше
**добавляет по одной зависимости под конкретную задачу** и объясняет каждую.

### Живая демонстрация: цена одной зависимости

Покажите `CLAUDE.md`, §6, пункт про нативные модули, и `apps/web/package.json` —
там `hash-wasm`, а не `@node-rs/argon2`. Один пакет, выбранный неудачно, стоил
проекту прохода: сборка на Linux сломала запуск на macOS.

Вопрос аудитории: как это поймать заранее? Ответ, который стоит услышать от них
самих, — **проверкой**, а не внимательностью.

### Проверка вместо намерения

В AGORA это тест `test_dependencies_declared.py`. Он разбирает исходники через
AST, собирает все внешние импорты — **включая объявленные внутри функций** — и
требует, чтобы каждое имя разрешалось в окружении.

Расскажите историю: `openai` импортировали четыре модуля, но в зависимостях его
не было. Не поймали ни сборка, ни CI, ни healthcheck — потому что тяжёлые
импорты сделаны внутри функций. Модуль импортируется, образ собирается, воркер
поднимается healthy, а `ModuleNotFoundError` ждёт первого обращения к модели, то
есть **после** оплаченных ffmpeg, транскрипции и разбора кадров.

Мораль, которую стоит продиктовать:

> Ошибка, которая проявляется поздно, дороже ошибки, которая ломает сборку.
> Проверки нужны не там, где страшно, а там, где отказ приходит с задержкой.

### Что стоит настроить в первый день

| Файл | Зачем |
|---|---|
| `tsconfig.json` — `strict: true`, пути `@/ → src/` | без strict TypeScript почти не ловит ошибки |
| `.env.example` | без него следующий разработчик не запустит проект |
| `lib/env.ts` с валидацией zod | отсутствующая переменная падает при старте, а не в проде |
| `.gitignore` — `.env.local` | см. раздел про секреты ниже |
| CI: `build`, `lint`, `tsc --noEmit` | правило, которое не проверяется, не действует |

## Что сказать про секреты (5 мин, обязательно)

Покажите `CLAUDE.md`, §6-бис. Там записан реальный случай: файл с выгрузкой
рабочего чата, содержавший root-пароль VPS и пароль базы, лежал в каталоге
репозитория. Один `git add -A` отправил бы его в историю навсегда.

Два правила, которые стоит записать:

1. **Всё, что попало в переписку, считается скомпрометированным.** Удаление
   сообщения ничего не отменяет — нужен перевыпуск.
2. **Узкая проверка хуже отсутствующей.** Метрика `secret_scan` в AGORA
   сканировала только семь расширений и два формата ключей — и была зелёной при
   живом пароле в дереве. Зелёная метрика создаёт спокойствие, которого нет.

Живой пример из этой недели: агент вывел в терминал переменные окружения
контейнера по маске `HF_*` и вместе с ними напечатал токен HuggingFace. Токен
пришлось перевыпускать. Ошибка не в агенте — в маске, выбранной не глядя.

## Резерв: что показать, если останется время

**Как выглядит потерянный проход.** Откройте `loop-state.json`, раздел
`failed_hypotheses` последнего прохода:

> «Воркер не видит скачанную модель и скачает 2.9 ГБ заново» — неверный вывод,
> стоивший прохода. Проверка шла через `try_to_load_from_cache`, который смотрит
> в стандартный кэш, тогда как код звал модель с `download_root=HF_HOME`. Модель
> на диске была. Последовавший «ремонт» переносом каталога сломал загрузку
> по-настоящему.

Это лучший учебный материал, какой бывает: отрицательный результат с названной
причиной. Мораль — **проверять тем же вызовом, каким работает код**, а не тем,
который кажется стандартным.

## Домашнее задание (предложение)

Инициализировать проект по своему ТЗ и сдать **не код**, а четыре файла:

1. `CLAUDE.md` — минимум три правила с указанием цены нарушения.
2. `docs/ARCHITECTURE.md` — стек и файловая структура, у каждого решения причина.
3. `tasks.json` — не меньше восьми задач с `blockedBy` и проверяемым `cdd`.
4. `README.md` — как запустить с нуля на чистой машине.

Критерий приёмки, который стоит объявить заранее: **другой студент по этим
файлам запускает проект и берётся за задачу, ничего не спрашивая у автора.**
Это ровно та проверка, которую проходит агент в новой сессии.
