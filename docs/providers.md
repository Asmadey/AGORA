# Провайдеры: агент TimeWeb и локальная диаризация

Разбор `api-1.json` (OpenAPI Cloud AI) и решение по pyannote. Обе темы здесь
вместе, потому что вместе они отвечают на вопрос «что уезжает наружу, а что
считается на своём железе».

## 1. pyannote можно ставить локально, и платить не нужно

Короткий ответ: да.

`pyannote.audio` — MIT, ставится обычным `pip`. Веса пайплайнов лежат на Hugging
Face в закрытых репозиториях, но закрыты они **принятием условий, а не оплатой**.
Нужен бесплатный HF-токен с правом чтения.

Платный продукт у них тоже есть — `speaker-diarization-precision-2`. Он
подключается через ту же библиотеку одной строкой, и это ловушка: код выглядит
идентично, но аудио уходит на серверы pyannoteAI. Для продукта, который
продаётся как self-host, это не оптимизация, а незаявленная передача данных
третьей стороне. Поэтому `DiarizationConfig` принимает только два локальных
пайплайна и отвергает premium с внятным сообщением, а не молча.

### Какой пайплайн брать

Вы нашли `pyannote-audio==3.4.0`. Работать будет, но актуальная линия — 4.x
(последний релиз 4.0.7 от 30 июня 2026), и в ней появился `community-1`:

| Бенчмарк | 3.1 (legacy) | community-1 |
|---|---|---|
| AMI (IHM) | 18.8 | 17.0 |
| AliMeeting | 24.5 | 20.3 |
| CALLHOME | 28.5 | 26.7 |
| DIHARD 3 | 21.4 | 20.2 |
| AVA-AVD | 49.7 | 44.6 |

Diarization error rate, %, меньше — лучше. Основной выигрыш `community-1` —
подсчёт числа говорящих и назначение реплик. Для нас это прямо по делу: мы режем
транскрипт по спикерам, и ошибка в числе говорящих искажает не одну реплику, а
всю разметку сцены.

Взят `community-1`, переключение — переменной `DIARIZATION_PIPELINE`.

### Чего в бенчмарках нет — и это важно

Цифры скорости из README (31 секунда на час аудио для `community-1`) измерены на
**NVIDIA H100**. Наш VPS — CPU-only по Decision Log #1. Эти числа к нам не
относятся никак, и я не буду выдумывать замену: реальную скорость на вашем
железе даст только замер. Сделать его нужно до того, как `task_time_limit` в
3 часа окажется мал для 12-минутного материала.

Порядок проверки: взять `evals/fixtures/short_60s.mp4`, прогнать диаризацию,
замерить, умножить на 12. Замер обязателен и входит в приёмку задачи #15.

### Silero VAD — не запасной план, а часть основной схемы

Первая редакция этого раздела перечисляла диаризацию только по речевым участкам
среди вариантов «на случай, если окажется медленно». Решение изменено 31.07.2026:
VAD стоит в схеме безусловно (Decision Log #6).

Причина проще, чем скорость. Диаризовать тишину, музыку и шум незачем
**независимо** от того, сколько занимает прогон: это работа, результат которой
заведомо выбрасывается. Для видеоконтента, где речь занимает половину дорожки,
экономия кратная, и держать такую вещь в резерве — значит платить за неё каждый
прогон, пока кто-нибудь не соберётся сделать замер.

Устройство: `silero-vad` отдаёт список речевых интервалов, pyannote получает их
**одним вызовом**, а не по одному на интервал. Это принципиально: диаризация по
отдельным кускам назначает метки спикеров независимо в каждом, и `SPEAKER_00` из
первого куска не имеет отношения к `SPEAKER_00` из второго. Глобальная
консистентность спикеров — требование Decision Log #6, и жертвовать ею ради
экономии нельзя: именно по спикерам режется транскрипт.

Проверяется это в CDD задачи #15 напрямую: диаризация по речевым участкам обязана
дать те же метки, что и по полному треку на фикстуре. Разойдётся — виноват способ
передачи участков, а не VAD.

### Практические детали развёртывания

- **ffmpeg обязателен** — 4.x декодирует аудио через `torchcodec`, который на
  него опирается. В `worker.Dockerfile` уже есть.
- **Веса качаются один раз** и кладутся в том `model_cache`. Если из сети
  развёртывания нет доступа к Hugging Face, воркер не поднимется вообще —
  тогда веса нужно положить в образ на этапе сборки.
- **Телеметрия.** 4.x по умолчанию шлёт анонимную статистику вызовов
  (длительность файлов, число говорящих). Выключено через
  `PYANNOTE_METRICS_ENABLED=0` и в образе, и в compose.
- **Кэш — в домашнем каталоге `celeryuser`.** Был дефект: том монтировался в
  `/root/.cache`, а контейнер работает под uid 1001 и в `/root` писать не может.
  Проявилось бы это на первой транскрипции, уже после загрузки видео.

## 2. Агент TimeWeb: три вещи, которые ломают обычный клиент

Сверено с `api-1.json`, endpoint
`POST /api/v1/cloud-ai/agents/{agent_access_id}/v1/chat/completions`.

### 2.1 Обязательный заголовок `x-proxy-source`

Помечен `required: true` в спецификации. OpenAI SDK его не отправляет. Без него
запрос отклоняется на транспортном уровне — до всякой модели, и сообщение об
ошибке про модель ничего не скажет.

```python
from openai import OpenAI
client = OpenAI(
    api_key=cfg.api_key,
    base_url=cfg.base_url,
    default_headers=cfg.default_headers,   # {"x-proxy-source": "agora"}
)
```

### 2.2 Поле `model` игнорируется

Дословно из спецификации: *«ID of the model to use. This field is ignored as the
agent has its own model configuration»*.

Отсюда два следствия, которые меняют архитектуру, а не только конфиг:

**Модель выбирается в кабинете, а не в коде.** `AI_MODEL` и `VLM_MODEL` больше
ни на что не влияют. Я оставил их как подпись для отчёта и снимка задачи — знать,
на чём считался прогон, всё ещё нужно, — но переключить модель через них нельзя.
Строку «Модель: qwen3.7-plus» в интерфейсе теперь нужно понимать как «так было
настроено», а не «так запрошено».

**Один агент — одна модель.** Развести рассуждение персон и разбор кадров по
разным моделям можно только двумя агентами с разными `access_id`. Под это заведён
`VLM_BASE_URL`; пустое значение означает общий агент. Это стоит решить осознанно:
разбор панелей кадров и отыгрыш персоны — очень разные задачи, и оптимальная
модель для них может отличаться.

### 2.3 Картинки — только по URL

`ImageUrlContentDto` требует `url`. Ни `base64`, ни `data:` в спецификации не
упоминаются вовсе; base64 встречается ровно один раз — в примере для
`input_audio`, не для изображений.

Для нас это не мелочь. Панели кадров генерируются воркером локально, и передать
их инлайном, по всей видимости, нельзя. Значит:

1. панель кадров грузится в S3 (`fc5722f6-…`, `s3.twcstorage.ru`);
2. генерируется presigned URL с коротким TTL;
3. URL уходит в `image_url`.

Из этого следует требование, которого раньше в задачах не было: **бакет должен
быть доступен из сети, откуда ходит агент TimeWeb**. Оба сервиса у одного
провайдера, так что скорее всего это так, но проверять надо явно — иначе
падение произойдёт на стадии разбора кадров, после транскрипции, то есть после
самой долгой части прогона.

TTL ссылки должен переживать очередь. Если панель загружена, ссылка выписана на
5 минут, а задача простояла в очереди 20 — разбор упадёт на протухшей ссылке.
Выписывать URL нужно в момент вызова модели, а не в момент загрузки файла.

**Проверить это первым.** Гипотеза «инлайн-картинки не поддерживаются» опирается
на молчание спецификации, а не на явный запрет. Один запрос с `data:image/jpeg;base64,…`
закроет вопрос за минуту и сэкономит весь путь через S3, если инлайн всё-таки
работает.

### 2.4 Что работает как ожидалось

- `response_format` поддерживает `json_object` и `json_schema` — структурный
  вывод для разбора кадров и ответов персон доступен без обходных путей.
- `tools` / `tool_choice` присутствуют.
- Есть `/v1/models`, `/v1/responses`, `/v1/conversations` — но `conversations`
  нам не нужны: контекст персоны собирается на нашей стороне и пиннингуется в
  снимке задачи, а серверная история диалога сделала бы прогон невоспроизводимым.

## 3. Что проверить одним заходом

```bash
set -a; source .env.local; set +a

curl -sS -X POST "$OPENAI_BASE_URL/chat/completions" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "x-proxy-source: $MODEL_PROXY_SOURCE" \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"Ответь одним словом: работает"}]}'
```

Затем то же самое с картинкой по публичному URL и, отдельно, с `data:image/...` —
второй запрос отвечает на вопрос из 2.3.

Из моей песочницы `agent.timeweb.cloud` недоступен (сеть по белому списку), так
что оба запроса за вами.
