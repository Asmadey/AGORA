# Ф4: план реализации через тесты

План четырёх последних задач — #28 чат по результатам, #29 «Поделиться»,
#30 перезапуск, #31 файл контекста. Все четыре имеют `blockedBy: [22]` и
начинаются после того, как `e2e_short` пройдёт в среде владельца.

Документ описывает **порядок работы**, а не желаемый результат. Требования лежат
в `evals/state/tasks.json` (поля `cdd` и `acceptance`) и здесь не переписаны —
скопированное требование расходится с исходником молча. Здесь то, чего в графе
нет: какой тест писать первым, что именно он ловит и почему написанный после
реализации тест бесполезен.

---

## 0. Общий порядок, одинаковый для всех четырёх

Из §3 `CLAUDE.md`, и он не декоративный:

1. **Красный тест** `evals/tests/test_taskNN_<имя>.py` по полю `cdd`. Запустить и
   убедиться, что он падает и **перечисляет невыполненные условия**. Тест,
   который падает с `ImportError`, ничего не проверяет — он проверяет, что файла
   нет.
2. **Реализация** до зелёного.
3. **Проверка**: `npx tsc --noEmit`, `npm run lint`, `npm run test`,
   `npm run build` в `apps/web`; `pytest -q` и `ruff check .` в
   `services/agent-core`.
4. **PR** по шаблону. Статус в графе не ставится автором (§4).

**Двухуровневый тест.** Статический уровень разбирает исходники и SQL и работает
где угодно, включая CI. Поведенческий требует живой среды и при её отсутствии
обязан писать SKIP с причиной, а не выдумывать результат. Пропуск, замаскированный
под успех, хуже отсутствующей проверки: он создаёт уверенность.

**Что уже готово и переиспользуется.** Не начинайте с нуля:

| Нужно | Где лежит |
|---|---|
| Изоляция персоны при генерации среза | `agent_core/respondent/run.py`, функция `build_slice` — чистая, без состояния |
| Тест изоляции | `evals/tests/test_task18_respondents.py` — берите его форму, а не пишите свою |
| Отсев утверждений без опоры | `agent_core/analytics/report.py`, `has_support` |
| Разбор отчёта для экрана | `apps/web/lib/report-view.ts` + `lib/report-view.test.ts` |
| Четыре состояния экрана | `apps/web/components/agora/States.tsx` |
| Скелет обработчика | `requireSession` / `withTenant` / `toResponse`, см. `docs/INTERFACE_REBUILD.md` §5 |
| Промпты как данные | Промпт-студия (#26): новый промпт заводится файлом в `prompts/` **и** миграцией засева |

**Порядок между задачами.** #29 и #31 независимы и могут идти параллельно в
разных worktree. #30 опирается на кэш разбора видео и лучше идёт после #28,
потому что обе трогают `tasks`. Рекомендуемая очередь: **#29 → #31 → #28 → #30**
— от самой изолированной к самой связной.

## 1. #29 «Поделиться» — начинать с неё

`blockedBy: [22, 21]` · `verifies: rls_tenant`

Первой — потому что это **единственный санкционированный обход RLS в системе**.
Всё остальное в проекте построено на том, что данные арендатора не покидают его
периметр; здесь заводится дверь наружу. Чем позже такая дверь появляется, тем
больше кода уже написано в предположении, что её нет.

### Что здесь на самом деле деливерабл

Не кнопка и не публичная страница. **Негативные тесты.** Кнопку видно, и её
отсутствие заметит любой; дыру в токене не видно никогда, пока по ней не придут.

### Красные тесты — писать в этом порядке

Порядок не случаен: сначала то, что должно быть закрыто, потом то, что должно
открываться. Обратный порядок даёт соблазн «пока сделаю открытым, закрою потом».

```
1. подобранный токен → 404            (не 403: 403 подтверждает существование)
2. чужой токен → 404
3. истёкший TTL → 410
4. отозванный токен → 410
5. публичная страница не отдаёт другой отчёт
6. публичная страница не отдаёт чат
7. публичная страница не принимает мутаций (POST/PUT/DELETE → 405)
8. валидный токен → ровно один отчёт, без логина
9. каждый просмотр пишется в аудит-лог
10. энтропия токена ≥ 128 бит
```

Условие 3 против 4 существенно: **истёкший и отозванный дают один код 410, но
разные записи в аудите.** Если их не различать, «ссылку отозвали» и «ссылка
протухла» станут неразличимы при разборе инцидента.

Условие 10 проверяется статически — по способу генерации в исходнике, а не по
выборке значений. `Math.random()` даёт правдоподобные на вид строки; отличить их
от `crypto.randomBytes` по десяти образцам нельзя.

### Ловушки

**Обход RLS оформляется политикой, а не снятием `FORCE` и не `BYPASSRLS`.** Это
§5 `CLAUDE.md`, и оно уже стоило прохода дважды. Правильная форма — отдельная
политика на `report_shares`, узкая по команде и по таблице, как сделано в
`06_owner_read_auth_tables.sql`. Политику видно в `pg_policies`; снятый `FORCE`
не видно нигде.

**Публичный сегмент — свой, а не `PUBLIC_PATHS: ["/api/share"]`.** Сопоставление
идёт по префиксу. Отдельный сегмент верхнего уровня, как `/api-docs`.

**Токен не логируется.** Ни в аудит, ни в лог доступа: лог утекает легче базы.
В аудит пишется идентификатор ссылки, а не сам токен.

### Проверка

`rls_tenant` обязан остаться `pass` **после** появления шеринга. Метрика проверяет
изоляцию из-под `agora_app`; если она позеленела за счёт снятия `FORCE`, она
позеленела ложно — отдельным условием теста проверьте, что `FORCE` на всех 16
таблицах на месте.

## 2. #31 Файл контекста аудитории

`blockedBy: [22, 24, 9]` · `verifies: persona_grounding`

### Главный тест — не про загрузку файла

Загрузка, разбор pdf/docx, дистилляция в портрет — механика, и она ломается
громко. Тихо ломается другое: **файл переопределяет заземление на корпус**, и
продукт перестаёт быть «прогнозом, а не догадкой», ничем этого не показав.

Поэтому первый красный тест такой:

```
эталонный прогон persona_grounding С ПРИЛОЖЕННЫМ файлом контекста остаётся green
```

То есть распределения по соцдему (порог ≤0.10) и калибровка баллов (≤1.0) не
уезжают. Файл уточняет лексику, контекст и специфику ниши — и только.

Тест на «файл повлиял» пишется вторым и слабее по формулировке: в промпт
`persona.generate` попала секция из портрета. Сильную форму («персоны стали
другими») сформулировать честно нельзя — генерация недетерминирована.

### Остальные красные тесты

```
пустой файл → генерация не падает, портрет не создаётся
нерелевантный файл → генерация не падает
файл арендатора A не виден арендатору B
конфликт файла с корпусом показан пользователю предупреждением
```

Последнее — не косметика. Молча разрешённый в пользу корпуса конфликт означает,
что пользователь загрузил файл, увидел «принято» и не узнал, что половина файла
проигнорирована.

### Ловушка

**Не заводить новый механизм.** По acceptance файл идёт через существующий
`portrait.distill` (#24) и дополнительной секцией в `persona.generate`. Соблазн
написать отдельный путь «файл → персоны» велик и даёт вторую формулу заземления,
которая разойдётся с первой.

## 3. #28 Чат по результатам

`blockedBy: [22, 26]` · `verifies: isolation_persona, qa_catches_injected`

Сейчас на месте чата — заглушка, честно называющая номер задачи
(`app/runs/[id]/chat/page.tsx`). До неё там стоял чат, работавший на вид:
функция отправки возвращала заготовленную строку, ни к какому маршруту не
обращаясь. **Это ориентир того, чего делать нельзя**, а не отправная точка.

### Архитектурное решение, которое надо удержать

Чат — **отдельный синхронный агент, не оркестратор**. LangGraph-поток живёт
внутри Celery-задачи, умирает вместе с ней и диалога не хранит. Попытка
переиспользовать оркестратор здесь выглядит экономией и даёт диалог, который
нельзя восстановить после перезапуска воркера.

### Красные тесты

**Режим «аналитик»:**

```
вопрос про метрику, которой в исследовании нет → insufficient_data == true
                                                 и выдуманного числа в ответе нет
каждое утверждение несёт таймкод или цитату      (переиспользовать has_support)
```

Второй пункт закрывается кодом, а не промптом: отсев в `analytics/report.py` уже
написан и работает. Просьба в промпте выполняется через раз и незаметно.

**Режим «персона»:**

```
вопрос про факт вне DNA → out_of_profile == true
в контекст персоны не попадают ответы других персон → утечка == 0
ответ, противоречащий её прежним → contradicts_previous == true
```

Тест изоляции — **тот же, что в #18**, а не новый. Одна и та же проверка в двух
формах разойдётся, и разойдётся молча.

**Треды:**

```
тред восстанавливается после перезагрузки страницы
тред одного арендатора не виден другому
```

### Ловушки

**`contradicts_previous` — суждение, а не арифметика.** Это работа модели.
Но `insufficient_data` и `out_of_profile` — ближе к проверяемому, и их стоит
подпирать кодом: если в отчёте нет поля, про которое спросили, это видно без
модели.

**Каждое сообщение — платный вызов.** Учитывается в капе стоимости из Настроек
(#27). Тест на превышение капа пишется вместе с фичей, а не после: без него кап
существует только на экране настроек.

**Схема тредов — миграцией.** `chat_threads` / `chat_messages` с RLS. DDL руками
через панель провайдера невидим для репозитория и стирается следующим
`migrate.sh` (§5).

## 4. #30 Перезапуск с новыми вопросами

`blockedBy: [22, 10, 6]` · `verifies:` пусто — это значит, что метрики гейта его
не покрывают, и CDD-тест здесь единственная защита.

### Главный тест — про деньги

```
перезапуск НЕ пересчитывает video_understanding: 0 новых вызовов VLM
```

Разбор видео — самая дорогая стадия конвейера. Если кэш родительской задачи не
подхватится, перезапуск будет работать правильно и стоить как полный прогон;
заметят это по счёту, а не по поведению.

Проверяется счётчиком вызовов, а не наличием кэша: «кэш есть» и «кэш
использован» — разные утверждения.

### Остальные красные тесты

```
режим «допрос»:  персона получает свои прежние ответы,
                 отвечает только на новые вопросы,
                 старые баллы в отчёте не меняются
режим «чистый»:  вся анкета заново, прежние ответы в контекст НЕ попадают
parent_task_id проставлен
отчёт показывает сравнение с родительским прогоном
```

Пара режимов проверяется зеркально: в одном прежние ответы обязаны быть в
контексте, в другом обязаны отсутствовать. Тест только на один из них пропустит
самую вероятную ошибку — что переключатель ни на что не влияет.

### Ловушка

**UI обязан объяснять последствия выбора.** Это в acceptance, и это не подпись
ради подписи: «чистый прогон» статистически честнее, но прежние баллы поедут, и
пользователь, ожидавший сопоставимости, получит несравнимые числа. Текст на
экране — часть контракта, и его отсутствие ловится статическим уровнем теста.

## 5. Что закрывается только прогоном владельца

Ни одна из четырёх задач не считается сделанной по статическому уровню (§4).
Поведенческие условия, требующие среды:

| Задача | Требует |
|---|---|
| #28 | живой ключ провайдера — сейчас 401 |
| #29 | живой Postgres с RLS, публичный домен |
| #30 | полный прогон с видео и его повтор |
| #31 | эталонный прогон генератора с приложенным файлом |

Ключ провайдера — общий блокер для #28 и для живых уровней #19 и #20. Его
перевыпуск разблокирует три задачи разом и стоит сделать до начала Ф4.

## 6. Порядок, если коротко

```
e2e_short зелёный в среде владельца
        │
        ├── #29 «Поделиться»      — начать с негативных тестов
        ├── #31 Файл контекста    — начать с persona_grounding под файлом
        ├── #28 Чат               — нужен ключ провайдера
        └── #30 Перезапуск        — начать со счётчика вызовов VLM
```

Каждая — своя ветка `task/<номер>-<имя>` и свой worktree (§2). `loop-state.json`
правится **одним коммитом в конце PR**, иначе конфликты гарантированы.
