## 2. RLS: вернуть инвариант, который обошли дважды

### 2.1 BYPASSRLS у `agora_login` — снять

На локальном Postgres роли `agora_login` выдан `BYPASSRLS`. Это прямо противоречит
`01_extensions.sql`, статической проверке в `test_task02_db_rls.py` и разделу 5 `AGENTS.md`:
`agora_login` — та самая роль, под которой приложение ходит в базу.

При этом атрибут, скорее всего, **не нужен**. Логин работает по другой причине: на
локальном инстансе таблицы и функции `SECURITY DEFINER` принадлежат суперпользователю
`agora`, а суперпользователь обходит RLS всегда, независимо от `FORCE`. То есть
`BYPASSRLS` здесь ничего не чинит, а только снимает страховку.

Проверка — одна команда и повторный вход:

```sql
ALTER ROLE agora_login NOBYPASSRLS;
```

Если после этого логин продолжает работать (ожидаемо), атрибут был лишним. Если ломается —
значит `SET LOCAL ROLE agora_app` где-то не выполняется, и это отдельный дефект, который
надо чинить, а не маскировать.

### 2.2 Миграция 06 — переделать

`06_no_force_auth_tables.sql` снимает `FORCE` с `teams` и `team_members` и объявляет это
единственным путём на managed-инстансе. Диагноз в комментарии верный: с `FORCE` владелец
тоже подчиняется политикам, политики заведены `TO agora_app`, для владельца подходящей
политики нет — значит ноль строк. Вывод из диагноза неверен.

Политики в PostgreSQL привязаны к ролям. Владельцу можно выдать **свою** политику, узкую и
проверяемую, не снимая `FORCE` и не требуя суперпользователя:

```sql
ALTER TABLE teams        FORCE ROW LEVEL SECURITY;
ALTER TABLE team_members FORCE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS teams_definer_read ON teams;
CREATE POLICY teams_definer_read ON teams
  FOR SELECT TO gen_user USING (true);

DROP POLICY IF EXISTS team_members_definer_read ON team_members;
CREATE POLICY team_members_definer_read ON team_members
  FOR SELECT TO gen_user USING (true);
```

Разница с `NO FORCE`: там владелец получал полный доступ ко всем командам и ко всем
таблицам; здесь — только `SELECT`, только на двух таблицах, и это записано политикой,
которую видно в `pg_policies`.

Проверяется на managed-инстансе за минуту, суперпользователь не нужен:

```sql
BEGIN;
ALTER TABLE team_members FORCE ROW LEVEL SECURITY;
CREATE POLICY tmp_definer_read ON team_members FOR SELECT TO gen_user USING (true);
SELECT count(*) FROM team_members;   -- под gen_user: ожидаем > 0
ROLLBACK;
```

### 2.3 Более чистый вариант — на потом

Обход владельца можно убрать совсем. Ввести `app.current_user_id()` по образцу
`app.current_tenant()`, и разрешить участнику читать **свои** строки членства:

```sql
CREATE POLICY team_members_self_read ON team_members
  FOR SELECT TO agora_app
  USING (user_id = app.current_user_id());
```

Тогда после проверки пароля (таблица `users` вне RLS) приложение ставит `app.user_id` и
читает членство под `agora_app` — без `SECURITY DEFINER`, без владельца, без исключений.
Правило «человек видит собственное членство» становится политикой, а не обходом.

Это требует правки `auth.ts` и новой миграции, поэтому идёт после 2.1 и 2.2.

## 3. Решить: локальный Postgres или managed

Переезд был вынужденным — из-за тупика с `BYPASSRLS`. Если раздел 2.2 подтвердится, повод
исчезает, и выбор надо делать по существу.

**За managed:** резервные копии, обновления и мониторинг делает провайдер. Локальный
Postgres в контейнере на VPS сейчас не имеет ни одного бэкапа — при потере диска теряются
все данные исследований.

**За локальный:** нет сетевой задержки и TLS-возни, полный контроль над ролями.

Отдельно и независимо от выбора — **размер VPS**. `AGORA_PRD_FINAL.md` §15 закладывает
8 vCPU / 16 ГБ / 100 ГБ. Заказан инстанс 2 vCPU / 4 ГБ / 40 ГБ, и на нём теперь ещё и
Postgres. С задачи #15 туда добавляются faster-whisper large-v3 (int8, порядка 2 ГБ
резидентно) и pyannote community-1 с torch. В 4 ГБ это не помещается, и упрётся оно не в
скорость, а в OOM-килл воркера посреди прогона.

Решать это надо до #14–#15, а не в момент падения.

## 5. Дополнить AGENTS.md по итогам смены

Раздел «ограничения, которые уже стоили проходов» пополняется двумя пунктами:

- На managed PostgreSQL нет суперпользователя и нельзя выдать `BYPASSRLS`. Схема
  безопасности не должна на них опираться: нужный доступ выражается политикой для
  конкретной роли.
- `BYPASSRLS` не выдаётся роли приложения ни при каких обстоятельствах. Если логин
  не проходит из-за RLS — заводится политика, а не атрибут роли.

И правило про исключения: снятие `FORCE` оформляется не комментарием в миграции, а
проверкой, которая падает, пока исключение не снято. Иначе временное решение живёт вечно.

## 6. Метрика `schema_drift`

Живая база и репозиторий за эту смену расходились трижды: снятый `FORCE`, выданный
`BYPASSRLS`, роли, заведённые руками в панели. Каждый раз это обнаруживалось человеком
задним числом.

Проверка в `evals/check.py`: сравнить фактическое состояние (`relrowsecurity`,
`relforcerowsecurity`, `pg_policies`, атрибуты ролей `rolsuper`/`rolbypassrls`) с тем, что
следует из миграций. Расхождение — красная метрика. Это дешевле любого протокола: правило,
которое некому проверить, нарушается молча.
