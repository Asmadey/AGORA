## 1. Executive Summary
Оценить сериал/ролик до релиза сегодня дорого и медленно (офлайн фокус-группа — недели и
десятки тысяч рублей за один показ в одном городе). **AGORA** генерирует синтетическую
аудиторию из AI-персон (цифровых двойников зрителей) по соцдем-параметрам, «показывает» им
видео и за минуты выдаёт аналитический отчёт — усреднённо по аудитории и по каждой персоне.
Отличие от «спросить у LLM»: (1) заземление на реальный grounding-корпус фокус-групп
(165 карточек респондентов), (2) реальный анализ видео (транскрипт+диаризация+разбор сцен),
(3) калибровка оценок по реальным распределениям, (4) изоляция ответов + QA-верификация,
(5) периметр РФ / self-host. ЦА — студии, онлайн-кинотеатры, продюсерские центры; MVP —
команды ≤10, мультиарендно. Позиционирование: **«прогноз, а не догадка»**.

## 2. Цели
**Бизнес:** ×кратно дешевле офлайн-группы; time-to-insight недели→часы; платящие пилоты
студий; expansion через переиспользование персон/портретов.
**Пользователь:** сигнал «зайдёт/не зайдёт» и *почему* до релиза; посегментные и по-персонные
инсайты со ссылками на сцены; итерация контента; сопоставимость между роликами на одной
аудитории.
**Не-цели:** замена реального исследования спроса; биометрия/RL-модели (Phase-2+); публичное
SaaS/биллинг на MVP; YouTube без скачивания; статистическая репрезентативность.

## 4. User Stories
- **Продюсер/шоураннер:** хочу за час сводный балл и разбор по сегментам, чтобы решить go/no-go до релиза.
- **Сценарист/режиссёр:** хочу видеть проседающие сцены и почему (цитаты+таймкоды), чтобы точечно переработать.
- **Маркетинг-аналитик:** хочу посегментные метрики (NPS, ретеншн, эмоции) для позиционирования.
- **Research lead:** хочу настраивать аудиторию/анкету/промпты и доверять заземлению.
- **Исследователь:** хочу переиспользовать набор персон на новом ролике для сопоставимости.
- **Владелец команды:** хочу изоляцию данных студии от других арендаторов.

## 5. Функциональные требования (P0/P1/P2 по impact)

**F. Знания/настройка.** P1 портреты аудиторий (.md-редактор + авто-дистилляция из датасета);

P1 **файл доп. контекста об аудитории** на шаге генерации персон (§20.4, фактическая
реализация — §21.10); P1 **«Статистика»** — расходы по данным биллинга (§21.3).
**G. Мультиарендность.** P0 RLS-изоляция, команды/пользователи/роли.
**H. Диалог и итерация (после первого green-гейта).** P1 **чат по результатам** в двух
режимах — аналитик по всему исследованию и допрос конкретной персоны (§20.1);
P1 **перезапуск с той же аудиторией и новыми вопросами** (§20.3).

## 7. Архитектура
**Frontend (TS):** Next.js App Router — UI, XState-визард, API-шлюз, отчёт, Промпт-студия,
Настройки, редактор портретов, Auth.js.
**Backend/ингест (Python):** FastAPI + **Celery** + **LangGraph**; ffmpeg/ffprobe,
**Silero VAD**, faster-whisper large-v3, pyannote **community-1**.
**Модели:** **Qwen 3.6** (мультимодальная) через OpenAI-совместимый **API timeweb.cloud** —
VLM-разбор кадров и рассуждение персон; Whisper+pyannote self-host на CPU. Абстракция
провайдера (`lib/ai-server.ts`, baseURL из env).
**Хранилища:** PostgreSQL+RLS; MongoDB; **Valkey** (очередь/прогресс/кэш); **S3 TimeWeb**
(медиа). Docker Compose. **TypeDB не используется** (графовая БД, не вектор; сходство — вектор
Phase-2). Общий контракт TS↔Python — canonical JSON Schema.

### 7.1 Граница данных: что покидает контур
Исходное видео и полная аудиодорожка **не передаются во внешнюю модель ни при каких
настройках**. Наружу уходят только производные материалы: панели ключевых кадров
(изображения), фрагменты транскрипта (текст) и структурированные срезы Content Pack.
Транскрипция и диаризация выполняются на своём железе, поэтому речь целиком остаётся
внутри контура.

Формулировка обязательна к соблюдению в коде: узел, отправляющий во внешний API байты
медиафайла или полный аудиотрек, — дефект, а не оптимизация. Причина в том, что продукт
продаётся как self-host, и «self-host» без описанной границы данных означает лишь место
установки, а не то, куда уходит содержимое исследования.

### 7.2 Единый источник таймкодов (proxy-представление)
На входе `ffprobe` проверяет пригодность файла, затем ffmpeg строит **proxy-видео**:
нормализованный контейнер с постоянным фреймрейтом и нулевым стартовым смещением. Все
последующие таймкоды — транскрипта, границ сцен, ключевых кадров, цитат в отчёте —
считаются от него.

Без этого шага `ffmpeg` при извлечении аудио, `PySceneDetect` при нарезке сцен и плеер в
интерфейсе считают время независимо. На переменном фреймрейте и при ненулевом
`start_time` они расходятся, и расхождение проявляется поздно — как «модель цитирует не ту
сцену», то есть выглядит дефектом качества оценок, а не дефектом конвейера. Отладить его в
таком виде дороже, чем предотвратить.

## 8. Бэкенд-пайплайн (LangGraph, внутри Celery-задачи)
State: `task_id, tenant_id, mode, video_ref, proxy_ref, audio_ref, speech_regions[],
segments[], transcript_diarized, chunk_analyses_ref, video_understanding,
content_pack_full, content_pack_compact, persona_ids[], survey, replication_count,
persona_answers[], qa_flags[], report, status, progress`.
```
probe_and_normalize(ffprobe → proxy-видео, единые таймкоды)
 → extract_audio → detect_speech(Silero VAD → speech_regions)
 → [ASR ∥ pyannote(community-1, по речевым участкам)] → merge_transcript
 → route(short|long) → sample_frames(PySceneDetect + fallback-интервал, дедуп, панели×4)
 → analyze_chunks(Qwen VLM → JSON сцены, MAP через Send)
 → stitch(REDUCE: video_understanding по таймлайну, транскрипт=позвоночник)
 → pack(Content Pack: полная и компактная форма)
 → evaluate_personas(Qwen, MAP, изоляция; каждая персона ×replication_count; пачки по 5)
 → qa(LLM-as-judge ×2: consistency/grounding/diversity; эскалация по низкому confidence;
      переспрос забракованных в пределах потолка — §21.5)
 → analytics(агрегат + групповой синтез + доверительные границы + нарратив)
 → REPORT_READY (+FAILED, чекпоинтер, прогресс в Valkey → SSE)
```
**Диаризация по речевым участкам.** Silero VAD выделяет отрезки речи, pyannote работает
только по ним, границы возвращаются в глобальные таймкоды. Диаризовать тишину, музыку и
шум не нужно, а на CPU-инстансе это прямая экономия времени прогона: заявленные
разработчиками pyannote 31 сек на час аудио измерены на H100 и к нашему железу не
относятся. Спикеры остаются глобально консистентными: pyannote получает все речевые
участки одним вызовом, а не по сегментам.

**Дедупликация кадров.** Из каждой сцены в VLM уходят только различающиеся кадры
(порог по перцептивному хешу). Статичная сцена длиной в минуту иначе даёт десяток почти
одинаковых панелей, каждая из которых оплачивается вызовом самой дорогой части конвейера.

**Content Pack в двух формах.** Компактная (сжатый таймлайн, ключевые сцены, эмоциональные
пики) уходит в массовый прогон респондентов; полная (все сцены, полный транскрипт,
раскадровки) — в контрольный глубокий просмотр по подвыборке. При 500 респондентах разница
между «каждому полный пакет» и «полный — контрольной подвыборке» измеряется разами
стоимости запуска, а не процентами.

Длинное видео: сегменты ~10 мин, параллельная транскрипция+VLM, глобальные таймкоды,
склейка. Кэш разбора кадров. Изоляция персон — структурная (в срезе state только своя DNA
+ Content Pack + survey).

## 9. Persona DNA + карточка + раздел «Персоны»
**DNA — 8 категорий** (Big Five 1–5; ~40–60 полей MVP → 120):
1. Демография (8–10); 2. Big Five 1–5; 3. Ценности/убеждения (5–8, ВЦИОМ+соц.приоритеты+
культ.взгляд+философия+отношение к будущему); 4. **Зрительское поведение** (8+: жанры,
толерантность к насилию/темпу/длине, лояльность к франшизам/актёрам, влияние рекомендаций,
реакция на идеолог./рекл. посылы, ожидания от продакшена, attention span); 5. Стиль общения
(5–6); 6. Принятие решений (5–6: риск/обдуманность/влияние сверстников/доверие авторитету);
7. Использование технологий (4–5); 8. Интересы/образ жизни (5+). + narrative + seed.
Guardrail: ответ ограничен задокументированным профилем.
**Карточка персоны — полный профиль, не подмножество.** Клик по плашке открывает карточку,
показывающую **все** атрибуты персоны: шапка (имя, должность, местонахождение, поколение,
род занятий, карьерный опыт, хобби) + все 8 категорий DNA с подписанными полями (Big Five
визуализировано) + narrative + seed. В контексте конкретного исследования карточка
дополнительно показывает ответы этой персоны, её цитаты с таймкодами и кнопку «Спросить
персону» (§20.1). Приёмка: ни одно непустое поле canonical JSON Schema не теряется
при рендере. **Раздел «Персоны»** в левом меню: сетка плашек (имя, поколение, род занятий,
дата) → карточка.

## 10-бис. Чат-агент по результатам (архитектурная позиция)
Чат (§20.1) — **отдельный синхронный агент, а не оркестратор.** Оркестратор — это
LangGraph-поток внутри Celery-задачи: он эфемерен, завершается вместе с прогоном и не
хранит диалог. Чат живёт поверх *завершённого* `task_id` и имеет read-only доступ к его
артефактам: `report`, `persona_answers`, `video_understanding` (с таймкодами), `survey`,
`qa_flags`. Данные ограничены (20–60 персон × ответы + отчёт), поэтому на MVP хватает
подачи в контекст без RAG; вектор — Phase-2 вместе с §7. Треды — в Postgres
(`chat_threads`/`chat_messages`, RLS по `tenant_id`).

**Как считается grounding-точность (уточнено 27.07.2026).** Порог |распределения−реальные|
≤ 0.10 по age_group/geo/gender проверяется **только на эталонном (reference) конфиге

включая пользовательские прогоны и прогоны с приложенным файлом контекста (§20.4) — именно
она держит «прогноз, а не догадку».

### 14.1 Эскалация QA на модель большего размера
QA-судья возвращает `confidence` вместе с вердиктом. Ответы, где он ниже порога, идут на
повторную проверку моделью большего размера; остальные закрываются основной. Смысл в том,
что дорогая модель вызывается там, где дешёвая созналась в неуверенности, а не на каждом
ответе — при 500 респондентах это разница в стоимости прогона, а не в его точности.

Реализация: `QA_ESCALATION_AGENT_ID` (отдельный агент TimeWeb со своей моделью — модель
выбирается в кабинете, а не в коде, см. `docs/providers.md`). **Переменная необязательна.**
Если она не задана, эскалации нет и все проверки идут на основной модели; это штатный
режим, а не деградация. Порог `QA_ESCALATION_CONFIDENCE` калибруется на первых прогонах:
назначать его до того, как известно распределение `confidence`, значит выдумывать число.

### 14.2 Экранный текст: OCR рассмотрен и не закладывается
Отдельный OCR-контур (Tesseract/PaddleOCR) в MVP не вводится: материал заказчика не
содержит субтитров и титров, а текст, попадающий в кадр эпизодически, читает сам VLM при
разборе панелей. Решение пересматривается, если в работу пойдёт контент с существенной
текстовой составляющей — рекламные ролики с плашками, новостные врезки, обучающие видео.

### 20.1 Чат по результатам исследования (задача #28)
На экране результатов завершённого `task_id` — диалог в двух режимах.
**«Аналитик»** — вопросы по всему исследованию («почему сегмент 45+ просел?», «какие сцены
теряют внимание?»). Отвечает только по артефактам задачи, каждый тезис — со ссылкой на
таймкод или именную цитату; нет данных → честное «в этом исследовании не измерялось»,
без правдоподобных достроек; факт и интерпретация разделены явно (промпт `chat.analyst`).
**«Спросить персону»** — допрос конкретной персоны из её карточки, как респондента после
фокус-группы. В контекст подаётся **только** её DNA + video_understanding + survey + её
собственные прежние ответы: та же структурная изоляция, что в основном пайплайне — персона
не знает ни других персон, ни того, что участвует в исследовании. Guardrail «ответ ограничен
профилем» действует: вне профиля → «не знаю», а не выдумка. Отслеживаются флаги
`out_of_profile` и `contradicts_previous` (промпт `chat.persona_followup`).
Архитектура — §10-бис. Стоимость: каждое сообщение — платный вызов, учитывается в капе (§12).

### 20.2 «Поделиться» результатом (задача #29)
Кнопка на экране отчёта создаёт **публичную read-only ссылку**: криптостойкий токен
≥128 бит, настраиваемый TTL, кнопка «Отозвать», список активных ссылок, аудит-лог просмотров.
Это **единственный санкционированный обход RLS** в системе — реализуется отдельной политикой
на таблице `report_shares` и обязан быть покрыт негативными тестами: истёкший токен → 410,
отозванный → 410, чужой/подобранный → 404, через публичную страницу недоступны другие
отчёты, другие арендаторы, чат и любые мутации. Публикуется полный отчёт; скрытие
поимённых персон — опция шеринга.

### 20.3 Перезапуск с той же аудиторией и новыми вопросами (задача #30)
«Перезапустить с этой аудиторией» на экране результатов. Переиспользуются `persona_set`
**и разбор видео родительской задачи** — VLM не пересчитывается (главная экономия, самая
дорогая стадия). Анкета дополняется новыми вопросами. Память персон — **выбор пользователя,
оба режима обязательны:**
- **«Допрос»** — персона получает свои прежние ответы и отвечает только на новые вопросы.
  Дёшево, непротиворечиво, старые баллы не двигаются; отчёт дополняется.
- **«Чистый прогон»** — вся анкета (старая + новая) задаётся заново в изоляции.
  Статистически чище, но прежние баллы могут поехать, и это дороже.

UI обязан объяснять последствия каждого режима для сопоставимости — это методологический
выбор пользователя, а не техническая деталь. Связь прогонов — `tasks.parent_task_id`.

### 20.4 Файл доп. контекста для генерации аудитории (задача #31)
На шаге «Аудитория» пользователь может приложить файл с дополнительным контекстом о
зрителях (pdf/docx/md/txt/xls). Файл **не создаёт нового механизма**: он дистиллируется в
«портрет аудитории» существующим промптом `portrait.distill` и подаётся в `persona.generate`
дополнительной секцией.
**Принцип приоритета — корпус выше файла.** Файл *уточняет* персон (контекст ниши, лексика,
специфика продукта), но **не переопределяет** распределения по соцдему и калибровку баллов
из grounding-корпуса. Иначе продукт скатывается обратно в «спросить у LLM» и теряет своё
единственное содержательное отличие. Конфликт разрешается в пользу корпуса и показывается
пользователю предупреждением. Приёмка: с приложенным файлом эталонный `persona_grounding`
остаётся green (§13).

# 21. Ревизия 22.08.2026 — что построено

Раздел написан по коду, боевой базе и замерам, а не по замыслу. Там, где он противоречит
§1–§20, прав он. Места, где реализация **отступила** от спецификации, названы отдельно и с
причиной: без причины отступление через месяц выглядит недоделкой, и его «чинят» обратно.

## 21.1 Распознавание речи: GigaAM вместо whisper и parakeet

**Что в каталоге.** `gigaam-v3-e2e-rnnt` (умолчание) и `large-v3`. `parakeet-tdt-0.6b-v3`
снят с предложения, но остаётся **исполнимым**: снимок настроек пиннит имя модели, и
убрать её отовсюду значило бы, что перезапуск прежнего прогона падает из-за решения,
принятого после него.

**Основание — замер, а не заявленный WER.** Полная дорожка прогона 0051 (3033 с, из них
1237 с речи по VAD), один скрипт и один детектор речи для всех:

| Состояние | Покрытие речи | Время | Пик памяти |
|---|---|---|---|
| parakeet, кусок 60 с — как шёл прогон 0051 | 59 % | — | — |
| parakeet, кусок 15 с | 80,0 % | 325 с | 1647 МБ |
| **GigaAM v3-e2e-rnnt** | **97,2 %** | 149 с | 1890 МБ |

Разница не только в покрытии. Один и тот же участок: parakeet — «Чи́сть и достоинство
гниют под каховкой. Темсот мальчишек»; GigaAM — «Честь и достоинство гниют под Каховкой.
700 мальчишек втоптали землю». Плотность слов при этом **одинаковая** (1876 против 1858):
первая редакция вердикта утверждала обратное, и это утверждение было ошибкой обобщения с
нетипичного пятиминутного окна.

**Две метрики покрытия, и путать их нельзя.** «Речь дошла до модели и дала текст» — 97,2 %;
«речь покрыта таймкодами слов» — 85,6 %. Разница это паузы между словами внутри
размеченного детектором высказывания. Порогом принята первая: именно она была 59 %.

**Границы кусков — из нашего VAD**, а не из `transcribe_longform` самого GigaAM: тот тянет
второй детектор речи, и две разметки одной дорожки разошлись бы в границах, а таймкоды
транскрипта перестали бы совпадать с таймкодами диаризации.

**Приёмка.** `COVERAGE_TARGET = 0.95` и поведенческий тест на настоящей дорожке; без
дорожки — честный SKIP. Подробности и оговорки — `docs/ASR_BAKEOFF_2026-08-20.md`.

## 21.2 Повторное обогащение персон: цена, которой не было в спецификации

Сборка аудитории идёт в две фазы: обогащение narrative у каждой персоны, затем **проверка
связности** LLM-судьёй. Не прошедшая персона **пересоздаётся с другим seed** и обогащается
заново — потому что расхождение могло прийти и от самих атрибутов, редкого сочетания,
которое связным текстом не описывается.

Что это стоит на боевом наборе из **60 персон**:

| Вызовов | Что |
|---|---|
| 60 | обогащение |
| 100 | проверок связности (30 персон пересозданы, 3 не прошли вовсе) |
| ~40 | повторных обогащений |

То есть **198 вызовов на 60 персон**. В спецификации фаза проверки описана, а её стоимость
— нет; на неё приходится две трети расхода на сборку аудитории.

**Половина персон не проходит проверку с первого раза.** Причину по сохранённым данным
установить нельзя: в базе лежит только финальный вердикт, а тот, из-за которого персону
забраковали, затирается вердиктом замены. В уцелевших текстах видно, что модель засчитывает
за расхождение «атрибут отсутствует в тексте портрета», хотя в том же вердикте сама пишет
«отсутствие упоминания не является расхождением». Это гипотеза с одним примером; чтобы
проверить, надо сохранять вердикт первой попытки рядом с финальным.

## 21.3 «Статистика»: расходы по данным биллинга

Раздел в левом меню. Таблица по дням: дата ДД.ММ.ГГГГ, объём каждой модели в миллионах
токенов, рубли с НДС, «Итого» за день. Внизу сумма по каждой колонке и резюме за период —
с НДС и без. Фильтр по модели, датапикер и пресеты «последние 7 дней» / «текущий месяц».

**Источник — API контроля затрат провайдера**, то есть тот же, по которому выставляется
счёт. Считать расход по своим логам вызовов было бы дешевле, но это вторая арифметика: она
расходится со счётом на округлениях тарифа и на всём, что провайдер тарифицирует иначе, — и
объяснять расхождение пришлось бы каждый месяц.

Строка SKU, не отнесённая ни к одной модели продукта, **не выбрасывается**: она видна
отдельной величиной и входит в «Итого». Иначе подключение третьей модели молча уменьшило бы
показанные расходы. Настоящие названия SKU закреплены тестом: на счёте они не такие, как в
примерах провайдера, а промах здесь невидим — незнакомая строка уходит в «Прочее», по
модели показываются нули, а «Итого» остаётся верным.

Доступ — только владелец: это деньги договора целиком, а не расходы одного исследования.
Ключи биллинга живут только в окружении. Без них раздел отвечает 501 и говорит, что не
настроен, вместо того чтобы показывать нули.

**Чему научил первый же отчёт.** За август: текстовая модель 28,05 млн токенов и 6 498 ₽,
vision — 0,98 млн и 52 ₽. Разрыв в 125 раз складывается из объёма (×28,7) и цены за токен
(×4,4). Изображения при этом уходят **только** в VL-модель — проверено по трассам: у
`analyze-frame` 233 картинки, у вызовов судьи, персон и отчёта их ноль.

## 21.4 «Поделиться» и «Скачать результаты»

**Публичная ссылка (§20.2).** Токен 256 бит выпускает сервер, в базе лежит только SHA-256,
адрес строится от источника запроса. Проверяет токен **база**, а не код страницы: политика
сверяет `app.current_share_token_hash()`, срок и отзыв, а роль `agora_share` не видит ничего,
кроме той ссылки. Ошибка в странице не может показать чужой отчёт. Область — весь отчёт либо
только сводка; просмотры пишутся в аудит-лог; отзыв одним действием.

> **Отступление от спецификации.** §20.2 требует «список активных ссылок» и код **410** на
> истёкший и отозванный токен. Списка нет. Код 410 не реализуется: `notFound()` в потоковой
> отрисовке отдаёт статус после начала ответа, поэтому вместо него показывается явная
> страница «ссылка недействительна» — одна на все три случая (нет, отозвана, просрочена),
> чтобы держатель ссылки не узнал, существовала ли она.
>
> **Почему функция так долго была витриной.** `report_shares.report_id` объявлен NOT NULL со
> ссылкой на таблицу `reports` в Postgres, а отчёты живут в MongoDB: в Postgres их 0 строк
> за всё время. Выпустить ссылку было нельзя в принципе. Миграция 38 переводит ссылку на
> **прогон** — это и есть то, чем делятся.

**«Скачать результаты».** Кнопка в шапке отчёта: расшифровка, отчёт в JSON, исходное видео.
Прежде три ссылки лежали секцией в середине отчёта — тот, кто пришёл забрать расшифровку,
листал отчёт целиком.

## 21.5 Отслеживание прогресса и QA-судья

**Прогресс.** SSE поверх снимка в Valkey; длительность каждого шага приходит в каждом
событии и переживает переподключение. После прогона источник правды — **Postgres**: статус
задачи и записанная длительность шага. До этой правки экран завершённого вчера прогона
показывал «Шаг 1 из 13» без единой галочки — снимок в Valkey к тому времени истекал, а
длительности приходили другим путём и рисовались. Время показывается словами: «2 часа
52 мин 14 сек» вместо «172:14».

**QA-судья.** Три проверки (grounding, consistency, diversity), LLM-as-judge. Забракованный
ответ **переспрашивается всегда**: порог «треть выборки» убран — он защищал бюджет не с той
стороны, отказывая там, где переспрос дёшев. Вместо порога — потолок числа попыток в
настройках (`requestionCap`, умолчание 15) и один раунд: вторая отбраковка окончательна.
Экран называет, что произошло: переспрос не понадобился / переспрошено N, вернулось M /
потолок исчерпан.

## 21.6 Настройка температур и моделей

Шесть стадий, каждая со своей температурой: **создание персон из датасета**
(`personaCreation`), **валидация персоны QA-агентом** (`personaValidation`), **симуляция
ответов персоной** (`responseSimulation`), **агрегация и анализ результатов**
(`aggregation`), **проверка ответов QA-судьёй** (`answerJudge`), **портреты сегментов**
(`segmentPortraits`).

Одного значения на конвейер быть не может: персона обязана получиться непохожей на
соседнюю — это условие метрики `response_diversity`, и низкая температура здесь даёт
двадцать почти одинаковых портретов. Судья же обязан быть воспроизводимым.

Рядом — выбор моделей по ролям (рассуждение, зрение, судья) и режим размышления отдельно
для основной модели и для судьи. Всё это пиннится в снимок прогона.

## 21.7 Управление доступом и мультиарендность

Роли — **owner** и **member**. Владелец распоряжается деньгами и настройками: промпт-студия,
ключ провайдера, «Статистика», приглашения. Участник ведёт исследования.

Изоляция арендаторов держится не на коде, а на базе: `FORCE ROW LEVEL SECURITY` на всех
таблицах, роль приложения `agora_login` объявлена `NOINHERIT` — забытый `SET LOCAL ROLE`
падает с «permission denied», а не работает тихо. `BYPASSRLS` не выдаётся никогда.
Нехватка прав лечится **политикой**, а не атрибутом роли: у владельца схемы есть узкий
`FOR SELECT` на две таблицы аутентификации, и он виден в `pg_policies`.

Публичная ссылка — единственный санкционированный обход, и он тоже сделан ролью
(`agora_share`) с политиками, а не флагом в коде.

## 21.8 Управление датасетом и портреты сегментов

Grounding-корпус собирается из XLS+DOCX, слепок фиксируется на наборе персон. **Портреты
сегментов** подключены к обогащению narrative по ключу `возрастная группа|гео|пол`: до
19.08.2026 раздел «Портреты» был отключён от продукта целиком — ни один узел конвейера его
не читал, хотя реестр промптов утверждал обратное.

Портрет входит в **ключ кэша** обогащения. Иначе две персоны с одинаковым скелетом из
разных сегментов получили бы один кэшированный narrative, собранный по чужому портрету, — и
выглядел бы он совершенно нормально.

## 21.9 API-документация и контракт

`/api-docs` — Swagger UI поверх собственной спецификации OpenAPI 3.1, отдаваемой по
`/api-docs/openapi`. Спецификация не декоративна: тесты сверяют её с кодом — каждый маршрут
описан, ключи `Settings` совпадают с `DEFAULT_SETTINGS`, `whisperModel.enum` — с каталогом
моделей, перечень статусов — со списком прогонов.

Сверка появилась после того, как спецификация разъехалась с продуктом, оставаясь зелёной:
прежняя проверка сверяла пути и методы — форму двери, но не то, что за ней.

## 21.10 Перезапуск и файл доп. контекста

**Перезапуск (§20.3).** Переносятся материал, набор персон и настройки исходного прогона.
Анкета не переносится: ради новых вопросов повтор и делают. Прогон без сохранённого набора
персон открывается с объяснением, чего не хватит.

> **Отступление от спецификации.** §20.3 требует два режима памяти персон («допрос» и
> «чистый прогон») и переиспользование разбора видео родительской задачи. Ни того, ни
> другого нет: сделан перенос входных данных в визард. Режимы памяти — методологический
> выбор, который надо показывать в интерфейсе с объяснением последствий, а переиспользование
> VLM требует связи `parent_task_id` в конвейере. Оба пункта остаются открытыми.

**Файл доп. контекста (§20.4).** Принимаются **только `.txt` и `.md`**, потолок **4000
символов**, текст попадает в системный промпт каждой персоны под собственным заголовком —
чужой текст, приклеенный к инструкциям, читается моделью как их продолжение.

Потолок посчитан, а не назначен: 4000 символов ≈ 1500 токенов, при 27 персонах и перекрытии
×3 это ≈121 000 токенов за прогон, около 4 % его расхода. Ограничитель здесь не окно модели,
а цена, помноженная на число персон.

> **Отступление от спецификации.** §20.4 называет pdf/docx/md/txt/xls и дистилляцию через
> `portrait.distill` в `persona.generate`. Реализованы два текстовых формата, и контекст идёт
> в промпт **респондента**, а не в генерацию персон. Причина: у первых трёх форматов
> содержимое требует разбора, и каждый — отдельная зависимость с собственным классом
> молчаливых отказов (пустая выборка вместо текста). Принцип приоритета корпуса при этом
> сохранён: контекст уточняет ответы, а не распределения.

## 21.11 Трассировка прогонов (не было в спецификации)

Каждый вызов модели уходит в LangFuse: разбор кадра, обогащение и проверка персоны, ответ
персоны, вердикт судьи, сборка отчёта. Ключи маскируются, предметные данные — нет: трасса,
из которой вырезано содержание, не отвечает ни на один вопрос, ради которого её открывают.

**Чего трассировка не покрывает:** распознавание речи. GigaAM считается локально, мимо
HTTP, и в трассе от него есть только длительность узла.

Три дефекта, которые нашлись только через трассы:
- **прогон длиннее часа исполнялся дважды** — `acks_late` с брокером Valkey и таймаутом
  невидимости в час; два пайплайна не помещались в память, и это выглядело случайным OOM;
- **промпт отчёта арендатора был заглушкой** `test {{content}}` с 3 августа: нарратив, темы
  и выводы не собирались вовсе, а `degraded` молчал;
- **служебная шапка промпта** проходила подстановку наравне с телом — ответ персоны уезжал в
  модель дважды, около трети токенов прогона.

## 21.12 Конструктор связей: происхождение числа

Под каждой метрикой отчёта раскрывается список ответов персон, из которых она посчитана, с
вербатимом и таймкодами; клик по таймкоду перематывает плеер. Формулы повторяют агрегатор
буквально, забракованные QA ответы не считаются — как и в агрегате. Если посчитанное
разойдётся с шапкой (аудитория больше первой страницы карточек), раскрытие говорит об этом
само: раскрытие, где сумма не сходится, превращает проверяемое число в спорное.

Из трёх вариантов конструктора (`docs/CONSTRUCTOR_OPTIONS.md`) сделан первый. Карта
происхождения данных и редактор схемы сборки персоны отложены: второй окупается после
двадцати исследований, третий ломает воспроизводимость, пока схема не версионируется.

## 21.13 Удаление исследования

Уходит всё, что прогон создал: строка в Postgres (каскадом отчёт, ссылки, чат), документы
`reports`, `report_personas` и `content_packs` в Mongo, и в S3 — исходный ролик,
перекодированная копия для плеера, заставка и кадры всех сцен.

До 21.08.2026 удалялся только исходный ролик: на боевой базе накопилось **36 осиротевших
пакетов материала из 41**. Заметить это было неоткуда — исследование пропадает из списка,
экран чист, а место занято.

Кадры удаляются по ключам **из самого пакета**, а не по префиксу: точный список того, что
создал прогон, и он не сотрёт чужое. Цена точности названа: пакет читается до удаления, и
если прочитать его не удалось, кадры останутся — об этом говорит ответ ручки, а не молчание.
