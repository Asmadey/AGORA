# AGORA — /goal (loop engineering, под ключ)

Петля идёт по графу задач AGORA (**31 задача**, `evals/state/tasks.json`,
согласован с `docs/AGORA_PRD_FINAL.md`). Верификатор двухуровневый: **per-task** (CDD
red→green на срез) и **project-level** (E2E-приёмка = green-условие всей петли). Пока
project-verifier не green — петля берёт следующую готовую по зависимостям задачу
(все `blockedBy` в статусе `done`) и доводит её до green.

> Pass 0 (бутстрап): до первого прохода должен существовать и запускаться одной командой
> `evals/check.py` + фикстуры + `loop-state.json`. Без верификатора green не измерим.
> **Статус на 27.07.2026:** `check.py` работает (`pass=1 fail=1 skip=13`), `short_60s.mp4`
> есть (синтетический testsrc — для субъективных оценок нужен реальный контент),
> **`long_12min.mp4` отсутствует** — его добавление входит в задачу #22.

```
/goal
ЦЕЛЬ («готово» = только измеримые пороги):
  tasks_done                     == 31/31 (все задачи графа status=done)
  build_frontend                 exit 0  (npm run build из корня монорепо → workspace @agora/web)
  build_worker                   exit 0  (pytest + ruff в services/agent-core)
  compose_health                 == all green (docker compose up -d, все healthchecks)
  e2e_short                      == pass  (fixture 60s → REPORT_READY ≤ 10 мин; report.aggregate есть; len(report.per_persona) == audience_size)
  e2e_long                       == pass  (fixture ~12 мин, mode=long → map-reduce → stitched → REPORT_READY)
  isolation_persona              == pass  (утечка контекста между персонами == 0)
  rls_tenant                     == pass  (кросс-арендаторный запрос → rows == 0)
  persona_grounding              == pass  (на ЭТАЛОННОМ конфиге генерации: |доля_сгенер − доля_реальн| ≤ 0.10 по age_group/geo/gender; |mean_score_gen − mean_score_real| ≤ 1.0 по каждому из 5 критериев — калибровка баллов проверяется ВСЕГДА, распределения только на эталонном прогоне)
  response_diversity             ≥ порог  (distinct-2 / дисперсия баллов ≥ X — нет mode collapse)
  qa_catches_injected            == true  (QA ловит подсаженный несогласованный ответ И выдуманный таймкод)
  prompts_editable               == pass  (все 13 ключей резолвятся из БД; tasks.prompts_snapshot заполнен)
  secret_scan                    == 0     (хардкод-ключей в исходниках нет)
  subjective_persona_realism     ≥ 7/10   (независимый LLM-оценщик, blind)
  subjective_report_quality      ≥ 7/10   (независимый LLM-оценщик, blind)

── 1. ВЕРИФИКАТОР (внешний, агент не оценивает себя сам) ──
  Объективное: evals/check.py — детерминированный скрипт. Поднимает docker compose,
    прогоняет pytest + playwright-e2e (short/long), скрипт grounding-статистики
    (сравнение распределений/средних сгенерированных персон с
    data/grounding/unified_respondent_sessions.json), isolation/RLS-тесты,
    secret-scan. Пишет JSON метрик + exit code. exit 0 = ВСЕ пороги достигнуты.
    Запуск одной командой: `python evals/check.py`.
    ВЛАДЕЛЬЦЫ МЕТРИК: каждая строка ЦЕЛИ закреплена за задачей графа через поле
    `verifies` в tasks.json — «ничьих» метрик нет. 10 из 15 проверок сейчас заглушки
    (`_todo` → skip); их реализация — часть соответствующей задачи, а не отдельная работа.
    ОБЛАСТЬ secret_scan: с задачи #1 REPO = корень монорепо, то есть покрыт весь
    репозиторий. Живой ключ переехал в .env.local (закрыт .gitignore). Каталог backup/
    со старыми репозиториями удалён — в нём лежали два утёкших ключа (AIza… и sk-…),
    их надо ПЕРЕВЫПУСТИТЬ: удаление файлов не отменяет утечку, если те репо публиковались.
  Субъективное (реализм персон, качество отчёта): независимый оценщик (другой LLM),
    рубрика 0–10, порог ≥ 7. Оценщик НЕ видит автора и его аргументов; на вход — только
    артефакт (сгенерированные персоны / нарратив отчёта) и рубрика.
  Правило приёмки: вердикт выносит ТОЛЬКО верификатор. «Я считаю, что готово» — не вердикт.
  Per-task: каждая задача графа имеет свой CDD-тест (red до реализации → green после);
    задача переходит в done только по green её теста + отсутствию регрессий в check.py.

── 2. СОСТОЯНИЕ (петля обязана помнить попытки) ──
  Файл: loop-state.json рядом с рабочими файлами. После КАЖДОГО прохода дописать:
    { "pass": n, "task_id": "<id из графа>", "did": "<что сделано>",
      "verdict": "<метрики check.py / ошибка>", "failed_hypotheses": [...],
      "next": "<следующая готовая задача + план>" }
  Перед КАЖДЫМ проходом прочитать: не повторять failed_hypotheses, начать с next.
  Источник истины прогресса: граф задач (evals/state/tasks.json — 31 задача, blockedBy).
  Источник истины данных: data/grounding/unified_respondent_sessions.json
    (grounding-корпус, 165 сессий) — только чтение; фикстуры видео — evals/fixtures/.
  Идемпотентность: генерация персон и прогон на фиксированном seed → повторный проход на
    тех же входах → diff == 0. Пайплайн резюмируется через LangGraph-чекпоинтер
    (падение на узле → продолжение с него, не с нуля). Перезапуск завтра = возобновление
    с loop-state.json + чекпоинтера, не с нуля.

── 3. УСЛОВИЕ ОСТАНОВКИ (ровно два выхода) ──
  Выход A: evals/check.py вернул exit 0 И оба субъективных ≥ 7 → финальный отчёт
    «метрика | порог | факт» по всем строкам ЦЕЛИ.
  Выход B: исчерпан лимит ≤ 40 проходов / ≤ бюджет (напр. 8 часов wall-clock, N API-вызовов,
    M токенов) → остановись и доложи: достигнутые метрики, loop-state, гипотеза блокера.
  Ранний выход B: одна и та же ошибка 2 прохода подряд ИЛИ 2 неудачные попытки одного
    фикса → не жги остаток лимита, докладывай (диагноз неверен — найди assumption под обоими).

── ПРОХОД (повторяемое действие) ──
  прочитай loop-state + граф → выбери следующую ГОТОВУЮ задачу (все blockedBy = done) →
  CDD: напиши падающий тест (red) → минимальная реализация → тест green →
  прогони релевантный срез evals/check.py → расхождение? почини минимальную причину,
  green не трогай → пометь задачу done → запиши loop-state →
  если project-verifier green → Выход A.

── ОТКАЗНЫЕ ВЕТКИ (заранее) ──
  LLM/VLM 429 / limit → backoff + retry (до 3), затем перенос прохода.
  LLM/VLM 403 / auth → перечитать ключ из env; не вышло → алерт, стоп-доклад.
  GPU OOM / модель не влезла → неактуально: модели по API, VPS CPU-only. Для Whisper на CPU —
    меньший batch / turbo-модель из Настроек.
  ffmpeg codec error → транскод в mp4/h264, retry.
  Whisper timeout на длинном видео → чанковая транскрипция + резюм через чекпоинтер.
  S3 upload fail / DB deadlock → retry с backoff.

── ГРАНИЦЫ ──
  Не выдумывай: только реальные ответы API/моделей или зафиксированные fixtures
    (evals/fixtures, data/grounding/*.json). Никаких «правдоподобных» цифр.
  Режимы: DRY_RUN (LLM/VLM/S3/БД замоканы, реальных трат нет) →
    CANARY (≤ 3 реальных вызова модели + 1 реальный прогон short-video, ТОЛЬКО после моего «ок») →
    LIVE. Необратимое существует только в CANARY/LIVE.
  Необратимые действия (за гейтом режимов): git push в новый репозиторий, деплой на TimeWeb,
    массовые платные вызовы моделей, удаление/миграция данных, перевыпуск ключей.
  Отчётность: молчание до выхода A или B. Эскалация только если реально нужен человек
    (креды, гейт CANARY/LIVE, необратимое решение).

── РОЛИ (субагенты) ──
  Оркестратор принимает работу ТОЛЬКО по вердикту верификатора (не по словам кодера).
  Поток на задачу: тест-писатель → критик тестов (задача — отвергнуть слабый тест, до 3 циклов)
    → кодер → финальный критик (регрессии + E2E). QA-агент проекта верифицируется отдельно
    подсадкой заведомо несогласованного ответа (должен поймать).

## Замечания по применению
- **Порядок обхода графа:** проверен топологически — 18 уровней, циклов нет. Критический
  путь: #1 → #2 → #3 → #7 → #10 → #11 → #13 → #14 → #16 → #17 → #18 → #19 → #20 → #21 → #22.
  Задачи #28–#31 (чат, шеринг, перезапуск, файл контекста) блокированы задачей #22 — они
  входят в `tasks_done`, но не имеют права отодвигать первый green-гейт `e2e_short`.
- **Нумерация:** канон — id из tasks.json (1–31). Старые документы используют ряд #9–#35;
  соответствие `legacy_id = id + 8`, карта — в AGORA_HANDOFF.md §6.
- **Бутстрап-порядок:** первые проходы обязаны поднять инфру (задача #1) и верификатор,
  иначе метрики не измеримы. Пока нет `evals/check.py` — green недостижим по определению.
- **Grounding как метрика, а не «на глаз»:** persona_grounding и response_diversity считаются
  скриптом против реального датасета — это и есть внешняя проверка «персоны похожи на людей».
- **Стоимость под контролем:** DRY_RUN гоняет всё на моках; реальные вызовы моделей — только
  в CANARY после явного «ок», иначе петля может сжечь бюджет на LLM.
