# AGORA — /goal (loop engineering, под ключ)

Петля идёт по графу задач AGORA (**31 задача**, `evals/state/tasks.json`,
согласован с `docs/AGORA_PRD_FINAL.md`). Верификатор двухуровневый: **per-task** (CDD
red→green на срез) и **project-level** (E2E-приёмка = green-условие всей петли). Пока
project-verifier не green — петля берёт следующую готовую по зависимостям задачу
(все `blockedBy` в статусе `done`) и доводит её до green.

> **Статус на 02.08.2026.** Bootstrap пройден: `evals/check.py` работает и содержит
> **16 метрик**. Закрыто 12 задач из 31. Инфраструктура развёрнута: VPS, Nginx, SSL,
> локальный PostgreSQL 18 в контейнере, managed MongoDB / Valkey / S3 на TimeWeb.
> Задача #3 (Auth) подтверждена поведенчески — 32/32.
> `short_60s.mp4` синтетический (testsrc); для субъективных оценок нужен реальный контент.
> **`long_12min.mp4` отсутствует** — его добавление входит в задачу #22.
> Над репозиторием работают несколько агентов в разных средах — см. `AGENTS.md`.

  persona_grounding              == pass  (на ЭТАЛОННОМ конфиге генерации: |доля_сгенер − доля_реальн| ≤ 0.10 по age_group/geo/gender; |mean_score_gen − mean_score_real| ≤ 1.0 по каждому из 5 критериев — калибровка баллов проверяется ВСЕГДА, распределения только на эталонном прогоне)

  subjective_persona_realism     ≥ 7/10   (независимый LLM-оценщик, blind)
  subjective_report_quality      ≥ 7/10   (независимый LLM-оценщик, blind)

── 1. ВЕРИФИКАТОР (внешний, агент не оценивает себя сам) ──
  Объективное: evals/check.py — детерминированный скрипт. Поднимает docker compose,
    прогоняет pytest + playwright-e2e (short/long), скрипт grounding-статистики
    (сравнение распределений/средних сгенерированных персон с
    data/grounding/unified_respondent_sessions.json), isolation/RLS-тесты,
    сверку живой схемы с миграциями, secret-scan. Пишет JSON метрик + exit code.
    exit 0 = ВСЕ пороги достигнуты. Запуск одной командой: `python3 evals/check.py`.
    ВЛАДЕЛЬЦЫ МЕТРИК: каждая строка ЦЕЛИ закреплена за задачей графа через поле
    `verifies` в tasks.json — «ничьих» метрик нет. Часть проверок ещё заглушки
    (`_todo` → skip); их реализация — часть соответствующей задачи, а не отдельная работа.
    ОБЛАСТЬ secret_scan: REPO = корень монорепо. Сканируются и код, и документы
    (.md/.sql/.sh/.json/.txt): выгрузка рабочего чата с root-паролем VPS однажды прошла
    мимо проверки именно потому, что та смотрела только код.
  Субъективное (реализм персон, качество отчёта): независимый оценщик (другой LLM),
    рубрика 0–10, порог ≥ 7. Оценщик НЕ видит автора и его аргументов; на вход — только
    артефакт (сгенерированные персоны / нарратив отчёта) и рубрика.
  Правило приёмки: вердикт выносит ТОЛЬКО верификатор. «Я считаю, что готово» — не вердикт.

  ── Что значит «задача done» (правило появилось после нарушения) ──
  Каждая задача имеет CDD-тест из ДВУХ уровней:
    статический    — разбирает исходники, схемы и SQL; работает где угодно, без БД;
    поведенческий  — требует живой БД, поднятого сервера, настоящих S3/Mongo/модели.
  Поведенческий уровень при отсутствии среды обязан писать SKIP, а не выдумывать результат.
  **SKIP — это не pass.** Статический green — необходимое условие, но НЕ достаточное.
  Задача переходит в `done` только когда её поведенческий уровень ПРОГНАН в среде с живой
  инфраструктурой и зелёный, и в check.py нет регрессий.
  Почему это записано отдельно: пять задач были помечены done по статическому green, при
  этом маршрут одной из них не компилировался вовсе, а сборщик датасета другой давал
  168 записей вместо 165 с пустыми стенограммами. `tasks_done` — гейтовая метрика; закрытая
  по статике задача превращает весь верификатор в отчёт о намерениях.
  Автор не закрывает свою задачу сам: `done` ставит тот, кто прогнал поведенческий уровень.

── 2. СОСТОЯНИЕ (петля обязана помнить попытки) ──
  Файл: loop-state.json в корне репозитория. После КАЖДОГО прохода дописать:
    { "pass": n, "task_id": "<id из графа>", "did": "<что сделано>",
      "verdict": "<метрики check.py / ошибка>", "findings": [...],
      "failed_hypotheses": [...], "next": "<следующая готовая задача + план>" }
  Перед КАЖДЫМ проходом прочитать: не повторять failed_hypotheses, начать с next.
  `failed_hypotheses` важнее остального: отрицательный результат экономит чужой проход,
    «всё получилось» не сообщает ничего.
  Чтобы не ловить конфликты, loop-state.json правится ОДНИМ коммитом в конце работы,
    а не по ходу — над репозиторием одновременно работает несколько агентов.
  Источник истины прогресса: граф задач (evals/state/tasks.json — 31 задача, blockedBy).
  Источник истины данных: data/grounding/unified_respondent_sessions.json — 165 сессий,
    ИСТОЧНИК ИСТИНЫ, а не выгрузка. Побайтово не пересобирается: срезы стенограмм получены
    моделью. Валидируется packages/shared/schemas/respondent-session.schema.json,
    происхождение и известные дефекты — в data/grounding/corpus.meta.json.
    Читать ТОЛЬКО через загрузчики (agent_core/grounding/corpus.py,
    apps/web/lib/server/corpus.ts) — иначе имена полей начнут угадываться в каждом месте.
    Фикстуры видео — evals/fixtures/.
  Идемпотентность: генерация персон и прогон на фиксированном seed → повторный проход на
    тех же входах → diff == 0. Пайплайн резюмируется через LangGraph-чекпоинтер
    (падение на узле → продолжение с него, не с нуля). Перезапуск завтра = возобновление
    с loop-state.json + чекпоинтера, не с нуля.

── ПРОХОД (повторяемое действие) ──
  синхронизируйся: git fetch --all → git log --oneline -15 → gh pr list --state open →
    git worktree list (что влилось, что делают прямо сейчас, кто где сидит) →
  прочитай loop-state + граф → выбери следующую ГОТОВУЮ задачу (все blockedBy = done,
    нет открытого PR) → заведи свой worktree и ветку task/<номер>-<имя> →
  CDD: напиши падающий тест (red, оба уровня) → минимальная реализация → тест green →
  прогони релевантный срез evals/check.py → расхождение? почини минимальную причину,
  green не трогай → PR по шаблону, с разделом «что НЕ подтверждено» →
  запиши loop-state одним коммитом → задачу в done ставит тот, кто прогнал поведенческий
  уровень → если project-verifier green → Выход A.

── ОТКАЗНЫЕ ВЕТКИ (заранее) ──
  LLM/VLM 429 / limit → backoff + retry (до 3), затем перенос прохода.
  LLM/VLM 403 / auth → перечитать ключ из env; не вышло → алерт, стоп-доклад.
  GPU OOM / модель не влезла → неактуально: модели по API, VPS CPU-only. Для Whisper на CPU —
    меньший batch / turbo-модель из Настроек.
  ffmpeg codec error → транскод в mp4/h264, retry.
  Whisper timeout на длинном видео → чанковая транскрипция + резюм через чекпоинтер.
  S3 upload fail / DB deadlock → retry с backoff.
  Запрос вернул 0 строк из заведомо непустой таблицы → это НЕ пропавшие данные, а RLS:
    смотри, от какой роли идёт запрос и есть ли для неё политика в pg_policies. Лечится
    политикой для роли, НЕ снятием FORCE и НЕ выдачей BYPASSRLS.
  permission denied на ALTER ROLE … NOSUPERUSER/NOBYPASSRLS → на managed-инстансе
    суперпользователя нет. Проверяй pg_roles, а не принуждай.
  docker compose config: «required variable … is missing a value» → не дефект compose:
    переменные объявлены через ${VAR:?...}, нужен --env-file .env.local.
  Тест падает трассировкой из-за старой версии библиотеки → это дефект теста: недостающая
    или устаревшая зависимость обязана давать SKIP с внятной причиной.

── ГРАНИЦЫ ──
  Не выдумывай: только реальные ответы API/моделей или зафиксированные fixtures
    (evals/fixtures, data/grounding/*.json). Никаких «правдоподобных» цифр.
  Режимы: DRY_RUN (LLM/VLM/S3/БД замоканы, реальных трат нет) →
    CANARY (≤ 3 реальных вызова модели + 1 реальный прогон short-video, ТОЛЬКО после моего «ок») →
    LIVE. Необратимое существует только в CANARY/LIVE.
  Необратимые действия (за гейтом режимов): миграции на живой базе, деплой на VPS,
    массовые платные вызовы моделей, удаление/миграция данных, перевыпуск ключей,
    push в main и force-push любой ветки.
  Разрушающие git-команды (reset --hard, checkout --, clean -fd, stash drop) выполняются
    только при чистом рабочем дереве. Сначала git status, потом команда: незакоммиченная
    правка, снесённая reset --hard, не восстанавливается ничем.
  `git add -A` перед коммитом — только после git status: в рабочий каталог попадают
    посторонние файлы, и они уезжают в историю под чужим сообщением коммита.
  Схема БД меняется ТОЛЬКО нумерованной миграцией в infra/postgres/init/, применяемой
    через migrate.sh. DDL руками через панель провайдера или psql запрещён: код не меняется,
    PR показывать нечего, а следующий migrate.sh молча вернёт схему к состоянию из
    репозитория. Метрика schema_drift существует именно для этого случая.
  Среда исполнения: сборка, тесты с живой БД и деплой идут на машине, где есть Docker,
    сеть до инфраструктуры и та же ОС, что в контейнерах. Каталог репозитория может быть
    смонтирован в другую среду — тогда node_modules общий, и npm из второй среды ломает
    первую. Нативные npm-модули в apps/web запрещены по той же причине (нужен argon2 —
    берите hash-wasm).
  Отчётность: после каждого прохода — запись в loop-state.json и PR с разделом «что НЕ
    подтверждено». Молчание до выхода A/B не годится: над репозиторием работает несколько
    агентов, и незаписанное для остальных не существует. Эскалация к человеку — если нужны
    креды, гейт CANARY/LIVE или необратимое решение.

── РОЛИ ──
  Внутри прохода: тест-писатель → критик тестов (задача — отвергнуть слабый тест, до 3

    отдельно подсадкой заведомо несогласованного ответа (должен поймать).
  Между агентами: несколько независимых агентов работают в разных средах и друг друга не
    видят. Протокол — AGENTS.md (симлинк CLAUDE.md): свой worktree, ветка на задачу, PR,
    прямой push в main запрещён. Всё, что не записано в репозиторий, для остальных не
    существует — включая изменения, сделанные прямо в живой базе.
  Ревью PR другим агентом имеет смысл только поверх зелёного CI: без объективного гейта
    оно вырождается в «выглядит хорошо». Машина ловит регрессии, агент — ошибки замысла

## Замечания по применению
- **Порядок обхода графа:** проверен топологически — 18 уровней, циклов нет. Критический
  путь: #1 → #2 → #3 → #7 → #10 → #11 → #13 → #14 → #16 → #17 → #18 → #19 → #20 → #21 → #22.
  Задачи #28–#31 (чат, шеринг, перезапуск, файл контекста) блокированы задачей #22 — они
  входят в `tasks_done`, но не имеют права отодвигать первый green-гейт `e2e_short`.
- **Нумерация:** канон — id из tasks.json (1–31). Старые документы используют ряд #9–#35;
  соответствие `legacy_id = id + 8`, карта — в AGORA_HANDOFF.md §6.
- **Согласованность графа:** если задача возвращается из `done` в `pending`, зависящие от
  неё задачи оказываются формально закрытыми поверх незакрытой. Такое противоречие нужно
  либо разрешать пересмотром зависимых, либо явно фиксировать в loop-state как принятое.
- **Grounding как метрика, а не «на глаз»:** persona_grounding и response_diversity считаются
  скриптом против реального датасета — это и есть внешняя проверка «персоны похожи на людей».
  Словарь схемы Persona DNA обязан совпадать со словарём корпуса по `age_group`, `geo`,
  `gender`: расхождение делает метрику невычислимой, и выяснится это на генерации персон.
- **Стоимость под контролем:** DRY_RUN гоняет всё на моках; реальные вызовы моделей — только
  в CANARY после явного «ок», иначе петля может сжечь бюджет на LLM.
- **Сгенерированные артефакты:** TS-типы и Pydantic-модели порождаются из canonical JSON
  Schema командой `npm run codegen` и правке руками не подлежат. Проверка «перегенерация
  совпадает с закоммиченным» обязана реально запускать генератор во временный каталог:
  `git diff` по неизменённому файлу всегда зелёный и не проверяет ничего.
