# Как настройки доезжают до воркера

Проект связки «Настройки (#27) → задача → транскрипция». Написан до реализации,
потому что здесь легко сделать работающе-неправильно: переключатель в интерфейсе
будет менять значение, а прогон — исполняться на старой модели, и заметить это
можно только по расхождению в тексте транскрипта.

## Что не так с нынешней схемой

Сейчас `WHISPER_MODEL` живёт только в `infra/docker-compose.yml` как переменная
окружения воркера. Из этого следуют три вещи:

1. Модель одна на весь сервер, а не на арендатора. Настройка per-tenant по PRD §12
   с этим несовместима в принципе.
2. Чтобы её сменить, нужен перезапуск контейнера. Переключатель в интерфейсе
   физически не может на неё повлиять.
3. Значение читается в момент исполнения. Задача, стоявшая в очереди во время
   смены настройки, доедет на новой модели — при этом в отчёте будет написано,
   что использовалась старая.

## Схема

```
   Настройки (UI)          PUT /api/settings          Postgres: settings
   ────────────────  ───▶  валидация contract   ───▶  (tenant_id, RLS)
                            lib/settings.ts
                                                            │
                                                            │ читается ОДИН раз,
                                                            │ при создании задачи
                                                            ▼
   Запуск прогона   ───▶   tasks.settings_snapshot  ───▶  payload задачи Celery
   (шаг «Резюме»)          jsonb, рядом с                 {"task_id": …,
                           prompts_snapshot                "settings": {…}}
                                                            │
                                                            ▼
                                      TranscriptionConfig.for_task(
                                          payload["settings"]["whisper_model"])
                                                            │
                                                            ▼
                                          faster_whisper.WhisperModel(cfg.whisper_model,
                                                                      compute_type=cfg.compute_type)
```

## Ключевое решение: снимок, а не ссылка

Настройки копируются в задачу в момент её создания и дальше не перечитываются.
Это то же решение, что и `prompts_snapshot` (Decision Log #10), и по той же
причине: **воспроизводимость отчёта требует, чтобы всё, что влияло на результат,
было зафиксировано вместе с результатом.**

Альтернатива — воркер читает `settings` по `tenant_id` в начале каждого шага —
выглядит проще, но ломается на длинном видео. Прогон на 12-минутном материале
идёт десятками сегментов; если между сегментами кто-то в команде переключит
turbo → large-v3, части транскрипта будут распознаны разными моделями. Различие
в качестве распознавания попадёт в текст, оттуда — в ответы персон, и разброс
оценок нельзя будет отличить от свойств материала.

Побочная польза: снимок отвечает на вопрос «на чём считался вот этот отчёт
трёхмесячной давности» без реконструкции истории изменений настроек.

## Что уже сделано

`TranscriptionConfig.for_task(whisper_model)` в
`services/agent-core/agent_core/config.py`:

- значение из снимка приоритетнее окружения;
- `None` (снимка нет — старая задача) откатывается на `from_env()`;
- невалидное значение бросает `ConfigError`, а не подменяется дефолтом. Молчаливая
  подмена — худший вариант: отчёт утверждал бы одну модель, а транскрипция шла бы
  на другой.

Список допустимых моделей продублирован в двух местах: `WHISPER_MODELS` в
`config.py` и `WHISPER_MODELS` в `apps/web/lib/settings.ts`. Дублирование
намеренное — интерфейс не должен уметь выбрать то, что воркер не умеет загрузить,
и проверять это надо с обеих сторон. При появлении третьей модели правятся оба
списка; тест `test_transcription_for_task_rejects_unsupported_model` фиксирует
поведение на невалидном значении.

## Что осталось

1. **Таблица `settings`** — задача #2 добавила её в схему; нужны только чтение и
   запись через слой `agent_core/db.py` с `tenant_scope`.
2. **`PUT /api/settings` пишет в Postgres** вместо памяти процесса. Меняются две
   строки в `apps/web/app/api/settings/route.ts`; контракт и валидация уже
   финальные. Требует `tenant_id` из сессии, то есть задачу #3.
3. **Колонка `tasks.settings_snapshot jsonb`** рядом с `prompts_snapshot`.
4. **Шаг «Резюме»** кладёт снимок в задачу при запуске и показывает выбранную
   модель в сводке — пользователь должен видеть, на чём поедет прогон, до нажатия.
5. **Стадия транскрипции** вызывает `TranscriptionConfig.for_task(...)` вместо
   `from_env()`. Это задача #13 (сборка пайплайна).
6. **Отчёт** показывает модель из снимка — иначе п.1–5 не проверяемы глазами.

CDD-критерий задачи #27 «смена Whisper large-v3↔turbo меняет используемую модель»
закрывается тестом уровня пайплайна: две задачи с разными снимками должны
инстанцировать разные модели. Проверка только через env этот критерий не
закрывает — она проверяет старую схему, а не новую.

## Кап стоимости и перекрытие

Те же правила. `cost_cap` попадает в снимок и проверяется счётчиком вызовов
внутри задачи; `default_replication` — это именно **дефолт для формы запуска**,
а не параметр исполнения: пользователь видит подставленное значение и может его
изменить, после чего в задачу уезжает уже `replication_count` из формы. Разница
существенная — настройка, которую нельзя переопределить на конкретном прогоне,
заставила бы менять командные настройки ради одного эксперимента.
